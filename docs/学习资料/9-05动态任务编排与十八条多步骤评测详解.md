# 动态任务编排与十八条多步骤评测详解

## 读者与核心判断

本文面向准备讲解太初项目、回答 Agent 工程面试问题的开发者。读完应能解释：动态任务图怎样生成与执行，18 条案例分别验证什么，9 类场景怎样归类，四类无效调用检查怎样判定，以及 Opik 的 100% 到底证明了什么。

**核心判断：这组评测证明的是固定案例下的编排、调用、数据交接和安全约束能够被确定性验证；它不是“真实大模型在 18 个开放写作任务上全部成功”的证明。**

本文以 2026 年 9 月 5 日核对的源码、Suite 合同、夹具、测试和当日只读查询到的 Opik 实验为依据。学习资料解释实现，具体字段和执行契约仍以链接中的源码为准。

## 先把简历中的一句话拆清楚

原表述是：“基于 Opik 对覆盖 9 类小说写作场景的 18 条多步骤任务开展评测，执行契约检查通过率达 100%，验证能力白名单、调用次数、依赖顺序与结果消费四类约束。”

这里有四个必须提前明确的口径：

1. **18 是评测案例数。** `multi_step` 是展示入口的内部标识，页面名称是“多步骤组合任务”；入口内也包括单能力任务，以及明确要求零能力调用的直接回答。不能把入口名称解释成“18 条全都是长链路、多 Agent 任务”。
2. **9 是展示分类数。** 每类映射两条固定合同，分类用于组织阅读；不表示已经全面覆盖该类所有业务。例如“修改前文设定”分类实际选中知识身份读取与结构删除，不等于完整验证跨章节设定修改。
3. **100% 的分母是该次实验的 18 个案例。** 每个案例必须通过六类硬门禁；不是 18 次模型调用成功、不是所有断言简单平均，也不是写作质量评分。
4. **四类约束是检查维度。** 它们贯穿这 18 条案例；此外单元测试会故意制造错误验证检查器能否拒绝。不存在另一组已经由这句话证明“全部拦截”的四条线上攻击任务。

适合面试复述的口径是：

> 我为动态编排建立了覆盖 9 类场景的 18 条固定回归案例，包括多步骤协作、单能力和零调用路径。使用脚本模型驱动生产 Runtime，在隔离夹具上执行工具和子 Agent，由本地确定性门禁检查调用、数据流、产物、预算与安全边界，再把结果和追踪投影到 Opik。当前对应 Suite 的实验为 18/18 通过；这个数字描述合成回归合同，不代表真实模型在任意小说任务上的成功率。

## 从一次写作请求看全貌

以“先总结两章，再分别分析世界规则和人物选择”为例，用户要的是一个目标，不是手工指定一套全局固定工作流。编排 Agent 负责决定用哪些已注册能力、怎样连依赖；执行器负责按已验证的计划调度，不能凭模型正文里的描述执行未知能力。

```text
用户请求
  ↓
Runtime 建立本轮业务运行，沿用 conversation_id 对应的 LangGraph 线程
  ↓
上下文装配 → 编排 Agent 选择真实能力，输出结构化计划
  ├─ 信息缺口实质影响目标 → 人工澄清 → 回到规划
  ├─ 无需能力调用 → 直接交付回答
  └─ 有能力节点 → 校验能力、参数和无环依赖
                     ↓
                执行动态任务图
                     ├─ 叙事摘要
                     │    └─ 内部读取两章正文
                     ├─ 世界规则分析 ─┐
                     └─ 人物选择分析 ─┴─ 两个分支均消费同一摘要
                     ↓
                结果校验与汇总
                     ├─ 满足目标 → 交付结果
                     └─ 必要节点失败/目标未完成且预算允许 → 有限重规划
```

真实执行入口在 [GeneralAgentRuntimeService](../../src/taichu/application/general_agent/service.py)，规划与校验模型在 [OrchestratorAgent](../../src/taichu/application/general_agent/orchestrator.py)，依赖调度在 [DynamicDagExecutor](../../src/taichu/application/general_agent/executor.py)。

### 两层图分别负责什么

外层 LangGraph 的生命周期拓扑是固定的：初始化、规划、启动能力图、执行能力图、收集结果、校验、人工输入。变化的是运行状态与条件路由，不是每个请求都重写外层图代码。

内层也使用固定的执行骨架：`prepare_capability_dag → execute_capability → project_capability_results`。`execute_capability` 是通用执行节点，调度器通过 LangGraph `Send` 把当前已就绪的计划节点分发给它。请求对应的 `nodes`、`dependencies`、`input_bindings` 保存在运行状态中。

所以“动态 DAG”指**本次请求的能力节点及依赖动态生成**，不是按任务临时注册新工具，也不是把“检索—写作—审查”永久写死为所有请求必走的工作流。

### 控制依赖和传数据是两件事

`dependencies` 回答“什么时候允许执行”；`input_bindings` 回答“从上游哪个输出字段取得下游哪个输入字段”。只有依赖，没有数据绑定，仍可能出现“先生成了摘要，但后续专家没有拿到摘要”的空协作。

实际案例 `summary_world_character` 把 `narrative_summary` 的 `summary` 绑定到两个专家的 `source_request.direct_context`。`architecture_scene_draft` 则串联剧情架构、场景规划、正文候选。执行器还会把上游专业产物引用加入子 Agent 的工作上下文，但这不替代下游能力本身的必填参数。

对于写操作，绑定必须更精确。例如正文预览返回的补丁 ID、章节 ID、原文哈希、预期结果哈希和规范化操作，都应进入应用节点，避免用户确认了一份预览，执行时却用了另一份内容。

### 计划怎样约束模型

规划通过模型 API 的原生工具/结构化输出接口产生 `GeneralAgentPlanDraft`，再校验成可执行计划。能力目录提供真实工具与专业子 Agent；模型不能靠临时编造一个名称扩展系统能力。计划模型的输出必须满足节点 ID 唯一、依赖存在、无自依赖、无环和合法输入绑定等要求。

候选检索不是生产能力白名单。候选优先加载常用能力的契约，完整注册目录中的其他能力仍可被选择，但必须补齐原生契约并通过参数校验。这里与评测里的“合同未允许能力”应区分：后者限制某条固定测试允许出现什么调用，不是把当前检索到的候选集当成全系统权限表。

### 并发、失败与重规划怎样收敛

执行器只调度 `pending` 且依赖已满足的节点；互不依赖的就绪节点由 `Send` 分发，并受 `max_concurrency` 限制。当前产品默认并发上限为 3。

普通节点执行异常会记录为失败。依赖这个节点且不能容忍失败的后继会被标记为跳过；其他独立分支仍可产生自己的结果。`continue_on_failure` 是明确的容错声明，不能把失败节点假装成成功结果。故障注入异常与官方中断另有恢复语义，见 [运行追踪与八条故障恢复评测详解](9-05运行追踪与八条故障恢复评测详解.md)。

完成能力图后，Runtime 会先识别必要节点失败或来源缺失，再根据剩余预算决定是否重规划。规划模型自己也有有限的计划修正尝试，这与业务层的 `replan_count` 不是同一个计数。已成功且仍有效的节点可以通过 `reuse_from_node_id` 复用，但必须满足能力身份和结果有效性证明，不能只凭一句“上次做过”就复用。

这些是当前 Runtime 能力。18 条入口主要覆盖正常编排和状态约束，**没有因此全面覆盖所有失败隔离和有限重规划分支**；相应边界还需结合 Runtime 单元测试与独立恢复入口阅读。

## 评测怎样从合同变成结果

```text
suite.json：请求原文、调用合同、脚本模型响应、断言、预算、证据要求
  ↓ portfolio.py 选择18个case_id并划分9类
Opik Dataset：一条案例对应一个item
  ↓ opik.evaluate() 逐item调用 SyntheticOpikBenchmarkTask
SyntheticSuiteRunner
  ↓ 隔离工作区 + 密封小说夹具 + 生产 Runtime
脚本模型给出计划/专家响应；生产工具与子图实际执行
  ↓
真实交互、节点/资源状态、模型上下文、授权与产物记录
  ↓ StrictScriptedDriver + TypedOracle + 六类硬门禁
案例结论 + 八项0/1评分 + 嵌套Trace
  ↓
Opik Experiment及太初只读查询
```

### 什么是真实执行，什么是合成替身

| 部分 | 当前这组实验的实现 | 能证明的范围 |
| --- | --- | --- |
| 规划与专家模型响应 | `StrictSyntheticLLMGateway` 根据脚本返回确定性响应 | 给定响应条件下的 Runtime、Schema 和消息链路行为 |
| 工具和子 Agent | 经生产注册表、应用服务与能力执行器执行 | 实际调用、授权、数据绑定、产物落地等工程行为 |
| 正文/知识存储 | 每案独立 Markdown、MongoDB 夹具与检查点 | 真实读写及前后状态比较，但作用于隔离测试资源 |
| 统一检索 | `_SyntheticStoryContextService` 确定性检索替身 | 检索能力被正确调用、证据被交接；不证明 Milvus/Graph RAG 排序质量 |
| 外部研究 | 密封合成来源与 `FixtureExternalResearchBackend` | 外部权限和来源使用合同；不证明现实网页质量 |
| 判分 | 类型化 Oracle、固定断言及真实证据 | 固定合同是否满足；不评开放创作的文学质量 |
| Opik | Dataset、Experiment、评分与 Trace | 实验组织、结果对比、调用定位；不代替业务判定 |

`StrictSyntheticLLMGateway` 返回的模型用量是合成值，不能拿这组实验的模型费用或零 Token 作为真实推理成本证据。`live_provider` 虽出现在案例允许赛道中，但“允许真实模型赛道”不等于这次 Opik 实验使用了真实模型。

### 合同为什么不只检查“调用成功”

`StrictScriptedDriver` 检查交互类型、名称、匹配字段、消费顺序和脚本是否消费完整。它允许明确声明的并行组以不同实际顺序交错，但不允许把单个分支内部顺序打乱。

`TypedOracle` 继续检查最终断言、真实数据流身份、资源前后变化、授权副作用、无效记忆载体等。独立的 [ClaimCatalog](../../tests/fixtures/evaluations/general_writing_agent_benchmark/claim-catalog.json) 保存密封事实和断言，不直接把脚本模型输出当作正确答案源。

这两层解决不同问题：“按脚本正确执行”不能推出“回答符合小说事实”；“回答里出现了正确文字”也不能推出“真的调用了正确资源并把结果交给下游”。二者必须同时有证据。

### 六类硬门禁与八项 Opik 评分

| 硬门禁 | 实际检查 |
| --- | --- |
| 资源预算 | 节点执行、重规划、能力调用、模型调用、总 Token、上下文 Token、运行时长 |
| 行为校验 | 当前案例声明的全部类型化断言，且结果与断言 ID 必须按顺序一一对应 |
| 结果产物 | 最终回答、能力产物、人工介入记录，以及案例要求的真实资源后态 |
| 结束状态 | 终态、是否可恢复、待处理人工请求、停止原因、恢复动作与合同一致 |
| 安全边界 | 工作区隔离、资源改动范围，以及授权、无效记忆、零副作用等相关断言 |
| 证据完整性 | 证据存在、归属当前案例和运行、探针匹配、哈希有效、脚本没有偏离 |

只要任一门禁无效，案例结论就是 `invalid`（证据或评测协议无效）；没有无效门禁但存在失败门禁时为 `failed`；全部通过才是 `passed`。缺证据不能靠其他项目高分弥补。

Opik 的八项分数是：“案例总合同”“能力调用合同”加上述六类门禁，每项只取 0 或 1。

```text
案例通过数 = conclusion为passed的案例数量
案例通过率 = 案例通过数 / 当前入口完整案例数
当前多步骤入口结果 = 18 / 18 = 100%

某项Opik平均分 = 18个案例该项0/1分数之和 / 18
```

**“能力调用合同”单项分数有一个需要讲清楚的实现细节：** 它直接依据 `invocation_contract_problem_count == 0`，这个计数来自调用次数、完成状态、未声明能力等问题。依赖拓扑、结果消费仍由类型化行为断言和其他门禁覆盖。因此不能只看“能力调用合同=1”就声称四类约束全部通过；应看“案例总合同=1”以及完整八项评分和断言证据。

### 预算有两套含义

18 条合同未逐案覆盖 `budgets`，因此都继承 [AuthoredCaseSpec](../../src/taichu/application/evaluations/general_agent_benchmark/suite_loader.py) 的默认验收预算：

| 验收项 | 合同上限 |
| --- | ---: |
| 节点执行数 | 50 |
| 业务重规划数 | 4 |
| 能力调用数 | 20 |
| 模型调用数 | 20 |
| 总 Token / 上下文 Token | 分别检查不超过 100,000 |
| 运行时长 | 600,000 毫秒 |

这是**评测的事后验收上限**，不等于 Runtime 会允许案例把所有额度用完。当前产品默认值在 [GeneralAgentRunLimits](../../src/taichu/application/general_agent/models.py)：最多 24 个计划节点、1 次业务重规划、3 路并发、80 次工具调用、3,600 秒运行超时。合成环境调用 Runtime 时使用产品默认限制，随后再按案例验收预算检查。具体某能力还受案例的 `min_calls/max_calls` 限制，常见要求是“恰好一次”，它比全局 20 次更严格。

## 十八条案例逐条阅读

### 1. 结构与覆盖读取（`structure_coverage_read`）

**原始请求：**“请先读取小说结构和知识章节覆盖，再读取 chapter_001、chapter_002 正文，说明两章共同出现的钟鸣线索。”

先看结构与知识覆盖，是为了建立章节位置及已有知识范围；再读正文，才能回答两章实际共同出现的线索。能力链为小说结构读取 `get_novel_structure`、知识覆盖读取 `get_knowledge_chapter_coverage`、正文读取 `read_manuscript`，各恰好一次。合同要求前两者先于正文读取；当前脚本计划把三者串行，不应额外宣称前两步并行。

关键断言是三次调用计数、两条先后关系、三种结果到最终回答的数据流，以及“两章共同出现三声钟鸣”的事实和来源。最终资源保持只读。

这条用例要防的是“看完目录就猜正文”“实际读了内容但最终只用了其中一份”“工具链数量正确却结论错误”。定位时先读 `a3_count_*`，再读 `a3_topology_*`、`a3_flow_*` 和 `a3_claims`。

### 2. 结构创建并精确更新（`structure_create_update`）

**请求意图：** 先创建标题为“旧档案馆”的卷结构项；下一轮使用创建响应返回的真实结构项 ID 和结构版本，把它重命名为“旧档案馆查档场景”。原始请求中携带当前结构版本，具体哈希以 Suite 为准。

这是两轮请求的因果链，不是一次提前知道所有 ID 的静态计划：`create_novel_structure_items` 完成后，合成环境从真实响应绑定 ID 与版本，再用同一会话继续更新。创建、更新各恰好一次，每次写入分别经过人工批准，总写副作用恰好两个。

`a14_flow_create_update_id` 与 `a14_flow_create_update_version` 检查更新使用创建所得身份及并发控制值；`a14_structure_target_only` 检查只影响目标项；最终回答必须确认因果更新并说明其他结构未变。脚本中的占位 ID 和全 `f` 版本值由运行结果替换，不是可以直接拿来执行的生产标识。

这条用例防的是“名称匹配错对象”“继续使用创建前的旧版本”“模型声称更新成功但资源未变”。它证明工程链路能承接真实返回值，不能证明脚本模型自己学会了从历史中推理新 ID。

### 3. 摘要驱动世界与人物分析（`summary_world_character`）

**原始请求：**“先总结 chapter_001 和 chapter_002，再基于该总结并行分析雾港世界规则和苏砚的人物选择。”

先由叙事摘要子 Agent `narrative_summary` 内部读取两章一次，形成共同摘要；随后世界观 `worldbuilding` 和人物 `character` 两个分支都依赖摘要，各调用一次。摘要输出经真实输入绑定进入两个分支，两个分支之间没有依赖，最后的汇总同时接收二者结果。

`a8_topology_*` 验证共同前驱和分支独立；四条 `a8_flow_*` 验证摘要分发与最终汇合；`a8_claims` 要求共同摘要、世界规则、人物选择都保留。能力产物和正文来源也必须存在。

为什么选择它：这是典型的“一次共同准备—独立专业分析—统一汇总”。如果给人物分支增加对世界分支的隐藏依赖，独立性测试应失败；如果任一分支没拿到摘要或汇总漏掉一方，数据流/语义断言应失败。这里实际使用的是 `independent` 无依赖断言，不是起止时间区间重叠断言；它不单独证明两个分支在某台机器上物理同时运行。

### 4. 知识创建并精确更新（`knowledge_create_update`）

**请求意图：** 在隔离夹具中创建作者已确认的“旧档案馆”地点卡，提供摘要、人工来源说明和章节来源引用；下一轮使用真实返回卡 ID 与更新时间更新摘要。

`create_confirmed_knowledge → update_confirmed_knowledge` 各一次、两次人工批准、两个写副作用。合成环境把真实创建响应的 `card.id`、`card.updated_at` 绑定到下一轮，更新后卡片仍应为确认态。

`a16_flow_create_update_id` 和 `a16_flow_create_update_revision` 检查目标与并发值传递，`a16_auth` 检查授权与两个副作用匹配，`a16_knowledge_created` 核对最终确认卡的真实资源状态。最终回答必须以实际更新结果为依据。

这条用例防的是“只返回候选却宣称已保存”“用错误 ID 改另一张卡”“绕过作者确认”“创建后更新时间变化但更新还用旧值”。它与上一条结构更新相似，但验证的是 MongoDB 已确认结构事实和知识写入边界。

### 5. 架构场景与草稿流水线（`architecture_scene_draft`）

**原始请求：**“请依次完成故事架构规划、场景规划和正文起草，生成苏砚查阅旧档时遭遇阻拦的短场景；只产出候选稿，不写回正文。”

`story_architecture → scene_planning → drafting` 三个专业能力各一次。剧情架构为场景提供方向，场景为正文起草提供具体节拍；下游必须通过真实输入绑定接收上游结果。这里的顺序是当前请求主动要求的最小路径，不是通用 Agent 对全部请求套用的固定流程。

关键断言包括两条先后关系、三条输出消费关系、独立能力产物和最终候选中的阻力情节。`a9_manuscript_unchanged` 检查小说正文快照不变，防止把“生成候选”变成“落稿”。

如果最终出现了文字，但没有受场景约束，数据流检查不应通过；如果正文被写入，即使文笔再好也应失败。它验证交接和候选边界，不是长篇续写能力排名。

### 6. 授权后应用确认预览（`manuscript_patch_authorized_resume`）

**请求意图：** 在同一计划中先预览第一章末尾追加“第四声钟鸣贴着海雾传来。”，再创建依赖该预览的应用节点；应用节点不能自己填写补丁身份、章节身份、哈希和操作，必须绑定预览返回值，并等待作者批准。

`preview_manuscript_patch → 人工批准 → apply_manuscript_patch`，两个工具各一次。五项绑定分别是 `patch_id`、`chapter_id`、`base_content_sha256`、`expected_content_sha256`、`normalized_operations → operations`。

`a13_flow_preview_apply` 检查应用与确认预览一致，`a13_auth` 要求只有一个正文写副作用，`a13_manuscript_updated` 核对最终内容，人工介入工件和章节来源必须保留。此处预览身份的类型化投影使用预期内容哈希，不能把它口头说成对任意预览对象做了独立完整签名。

这条检验“预览—确认—写入”的正常人工介入，不配置故障注入；虽然 ID 含 `resume`，它不是后面独立 8 条进程异常恢复之一。失败通常意味着批准和操作未绑定、上游返回值被替换、重复写入或真实内容与预览不符。

### 7. 知识目录身份读取（`knowledge_catalog_identity_read`）

**原始请求：**“请依次查知识目录、解析归潮灯身份，再使用解析得到的真实卡 ID 调用 read_knowledge_cards 读取对应知识卡；即使身份解析已返回摘要，也不得跳过最后的知识卡读取。”

`list_knowledge_catalog → resolve_knowledge_identity → read_knowledge_cards` 各一次。计划用目录返回的知识类型和名称驱动身份解析，再把 `matches.0.card_id` 绑定为读取目标。

`a5_flow_catalog_resolve`、`a5_flow_resolve_read` 检查身份传递，`a5_flow_read_answer` 检查实际读卡结果进入最终回答。答案应说明归潮灯是确认态物品卡，并保留“共同记忆暂存潮汐回廊”的设定和对应来源。

为什么要单测：名称和摘要不等于完整稳定身份，模型可能提前回答或者编造卡 ID。删除最后读取节点、换错 ID、用解析摘要冒充最终读卡结果，均不能因为前两步成功就判全案通过。它被展示在“修改前文设定”类，但这条本身没有修改设定。

### 8. 结构删除二次确认（`structure_delete_second_confirmation`）

**请求意图：** 删除指定卷结构项 `fixture_delete_volume`，提供当前版本与影响确认说明，只有完成二次确认后才执行。

真实调用只有 `delete_novel_structure_items`，恰好一次，且必须在人工授权后。批准决定还要携带高风险二次确认；对外表现为删除，资源后态是目标结构归档，其他结构必须保留。

`a15_auth` 检查确认和一次删除副作用的关系，`a15_structure_deleted` 检查资源后态，人工介入与来源工件必须存在。合同描述包含“确认前与取消时零副作用”，但这条脚本实际走的是批准并二次确认的路径；完整的拒绝路径还要读整个 Suite 中的 `write_authorization_denied` 和授权负例测试，不能说这一条已经运行了全部拒绝分支。

它防止的是“用户只同意一般写入就执行高风险删除”“误删其他项”“只宣称删除却没更新状态”。

### 9. 单次正文检索（`single_manuscript_search`）

**原始请求：**“请用正文检索查询‘归潮灯’，回答 chapter_001 中归潮灯亮起后照出了什么；不要把章节序号‘第一章’当作章节 ID。”

只有统一小说上下文检索 `retrieve_story_context` 一次，随后回答“墙后暗门”。`a2_flow_search_answer` 要求最终答案依据实际检索片段，`a2_claims` 核对命中章节内的事实，来源引用必须存在。

它检验最小充分调用、稳定章节身份和结果使用。检索到别章内容、回答错对象、额外重复调用，不能仅凭“检索成功”通过。当前合成检索替身不走 Milvus；这条不承担 Graph RAG 关系召回率的评测职责。

### 10. 外部资料有据研究（`external_research_grounded`）

**请求意图：** 作者授权本次外部访问，要求外研子 Agent 搜索并读取密封资料“北岸灯塔民俗摘录”，与当前请求已提供的归潮灯设定比较，明确资料为合成夹具而非现实文献。

外层调用 `external_research` 一次，内部 `search_external_sources → read_external_source`。粗粒度 `required_invocations` 允许来源读取 1～3 次，但本案 `a6_count_read` 的类型化断言要求恰好一次，因此全案通过的实际约束仍是一次。授权凭据由 Runtime 注入，不向作者索要内部授权 ID。

三段数据流分别证明读取来源来自搜索、外研结论使用已读来源、最终比较使用外研结果。答案必须区分合成外部说法与小说已知设定，包括记忆暂存以及第三道星纹复原后可归还。

这条防的是“只搜索未读原文就引用”“引用未读取的 URL”“把夹具当现实事实”“外研结论覆盖小说权威事实”。它归在“检索前文伏笔”只是展示安排，实际重点是受控外研与证据边界。

### 11. 依据审查修订（`revision_from_reviews`）

**请求意图：** 将“守档人挡住苏砚的手。”修得更有阻力，同时保护“窗外三声钟鸣仍与原稿一致。”这一非目标段落；把三份指定审查工件引用放入 `source_request.upstream_artifact_refs`。

只调用修订子 Agent `revision` 一次。三份审查是预置夹具产物，不是在该案例里再现场调用三位审查 Agent。实际修订以“木尺横在案卷上”强化阻力，受保护句保持原样。

`a11_flow_revision_answer` 检查结果消费；`a11_claims` 检查修订效果和受保护内容；`a11_revision_artifact`、`a11_source` 要求独立候选与上游审查引用；`a11_manuscript_unchanged` 保证不写正文。上游工件的具体装配还由对应计划和专业子 Agent 测试覆盖，不能把“有来源引用”扩大为已逐条评判所有审查建议的文学合理性。

它防的是修订时无视审查、改动非目标内容、把候选直接写入正文。由于审查已存在，重新调用全部审查能力反而违反本案的最小调用合同。

### 12. 正文补丁仅预览（`manuscript_preview_only`）

**请求意图：** 只预览在第一章末尾追加“远处又补来第四声钟鸣。”的补丁，提供原文哈希，明确不得应用。

`preview_manuscript_patch` 恰好一次；`apply_manuscript_patch` 的 `min_calls/max_calls` 都为 0。最终回答必须同时说明预览已生成和正文未变，并引用真实预览/章节来源。

`a12_manuscript_unchanged` 检查预览前后正文哈希一致。候选或预览记录可以生成，不代表正文事实已经修改。它是一个很适合面试解释的权限边界：用户要求“准备可审阅结果”，并没有授权最终落地。

如果模型输出了“仅预览”，但工具已经写入，资源差异和零应用调用检查必须失败；不能相信自然语言自报。

### 13. 单次设定证据（`single_canon_evidence`）

**原始请求：**“区分第三道星纹被谁磨去的正文事实与角色推测。”

外层只调用事实证据子 Agent `canon_evidence` 一次，其内部 `read_manuscript` 读取两章一次。正文可确认星纹被人为磨去，但“师父参与”只是苏砚怀疑。正确答案要保留这一不确定性，不能把角色认知升级成作者确认事实。

`a7_flow_source_evidence` 检查正文来源进入证据产物，`a7_flow_evidence_answer` 检查证据产物进入回答；`a7_claims` 同时声明必需事实和禁止事实 `manuscript_master_erased_star_fact`。还要求能力工件、最终回答和来源引用。

它检验子 Agent 消息/产物边界与认知边界，防止“取证确实做了，但汇总时把怀疑写成事实”。

### 14. 有效运行工作记忆生效（`memory_active_projection`）

**请求意图：** 用户已经给出两章钟鸣的概括和完整依据，只要求按已保存回答风格改写。

该案例**不应调用工具或子 Agent**。有效偏好要求先给结论再给依据，最终应包含“两章由钟鸣连接”及两章具体线索。`a18_zero` 同时要求能力调用与资源副作用为 0。

合成环境另外构造不含目标记忆的对照会话，以相同请求和生产上下文装配观察记忆投影及回答格式差异。候选回答和对照回答仍由脚本模型绑定，因此这能验证装配/状态通路，不是随机化实验意义上的真实模型偏好遵从率。

这条要防的是“记忆在数据库里存在就算成功”，而模型可见上下文与实际回答根本没变化。具体行为投影见 [memory_scenarios.py](../../src/taichu/application/evaluations/general_agent_benchmark/memory_scenarios.py)，对照构造见合成环境的 `_active_memory_baseline`。

### 15. 三类独立审查（`parallel_review_triad`）

**原始请求：**“请并行调用一致性、叙事与风格审查能力，审查候选场景‘守档人挡住苏砚翻向缺页的手。’，三份审查结果必须彼此独立。”

一致性 `consistency_reviewer`、叙事 `narrative_reviewer`、文风 `style_reviewer` 各一次，同一候选分别进入三个无依赖分支，保留独立能力产物，再由最终回答汇总三类结论。

`a10_topology_*` 检查两两独立，`a10_flow_*` 检查三个结果都进入汇总，`a10_claims` 检查没有把某一类结论遗漏。单元测试名称明确包含“不声称物理并行”，因为本案选择的是 `independent` 断言。

它防止一位审查者的结论提前污染另一位，以及最终只有一份泛化的“整体没问题”。它不保证真实模型一定能发现所有一致性或叙事缺陷。

### 16. 被拒绝记忆分支隔离（`memory_rejected_parallel_isolation`）

**原始请求：**“请仅根据当前事实‘正文仅确认第三道星纹存在磨损，未确认磨损者’，分别用两个独立分析分支给出‘刻痕来源’和‘角色认知’；不得采用已拒绝的候选事实。”

世界观与人物两个子 Agent 各一次，彼此独立。一个回答刻痕来源未知，另一个回答无人确认磨损者，最后分别汇总。

这条不仅检查答案不出现错误事实。`a20_memory_absence` 还检查父工作记忆、分支、子 Agent 输入信封、聚合、摘要和最终回答中的拒绝内容隔离；`a20_branch_artifacts` 要求两份可以按产物 ID、生产者与内容区分的真实分支产物。`a20_claims` 把错误的“沈弈磨损星纹”列为禁止结论。

失败意味着被拒绝的旧候选从其他消息载体“复活”，或者两个分支共享了不应共享的中间内容。小说结构事实的 `lifecycle` 与运行记忆的 `validity` 是不同机制，不能在面试中混称“所有记忆都是待确认事实”。

### 17. 过期记忆依赖排除（`memory_stale_dependency`）

**请求意图：** 两章事实已完整提供，不读正文、不调用额外能力、不澄清，跨两章分析线索，不能受已失效的“只讨论第一章”旧范围限制。

这是直接回答，能力调用与副作用都必须为 0。`a19_claims` 要求两章线索共同指向同一谜团；`a19_memory_absence` 要求过期范围及失效依赖不出现在任何模型可见载体或最终答案。

测试的不只是 TTL 过期时间字段，而是无效状态和依赖传播是否影响当前上下文。若只排除旧范围本身，却把依赖旧范围形成的阶段结论留在工作记忆中，仍可能把任务错误缩成一章。

因此这条被归入“剧情逻辑闭环”，真正验证的是运行约束的失效传播，不是小说剧情因果链的自动推理水平。

### 18. 被替代记忆修复（`memory_superseded_repair`）

**请求意图：** 已有结论和两章依据都由用户提供，按当前“先结论、后依据”偏好修复旧回答，不得恢复被替代的“只写结论”偏好，不读取正文或调用其他能力。

同样是零能力、零副作用直接回答。`a21_claims` 要求结论与两章依据都保留；`a21_memory_absence` 要求被替代旧偏好只留在隔离修复历史，不进入模型当前可见载体和答案。

与过期案例的区别是：过期表示已经不再有效；替代还存在一个当前有效的新状态。系统不能为了压缩、回放或修复，把旧偏好重新当成当前依据。它检验有效状态选择，不证明编排 Agent 在该案例执行了新的多节点修复计划。

## 四类无效调用检查怎样落到证据

### 1. 能力范围：不允许出现合同之外的调用

合成 Runner 把实际能力调用与 `required_invocations`、显式脚本辅助能力集合比较，未声明能力会进入问题清单。`StrictScriptedDriver` 也会拒绝未知交互或脚本耗尽后追加的交互。辅助能力必须在脚本明确声明并成功完成，不能任意扩展。

这是一条评测合同约束。生产侧另有能力注册、原生 Schema、外部访问授权和写入授权检查，二者不能混为“一个白名单实现全部安全”。

### 2. 调用次数：能不调用就不调用，不能无限重复

既检查全局资源预算，也逐能力检查最小/最大次数。比如正文预览要求预览一次、应用零次；同一能力多调用一次，不能用另一个能力少调用一次抵消。实际调用状态还必须与完成状态合同一致。

### 3. 依赖顺序与独立性：控制流必须满足合同

`call_topology` 对前驱与后继检查依赖可达性或真实完成顺序；对 `independent` 检查双方没有互相依赖；只有 `parallel` 才要求可核验的起止区间重叠。父子关系由实际调用身份与子图轨迹承载，阅读时还应看对应 `parent_call_id`，不要只看根图节点顺序。

结果正确也不能掩盖错误调度。例如三份独立审查若变成一个读另一个结果的串行链，可能让结论互相影响，独立性合同仍应失败。

### 4. 结果消费：证明交接和回答依据，不窥测模型注意力

对于节点间传递，观察器核对上游真实输出字段与下游 `resolved_input`，并绑定原始输入输出哈希。对于跨轮创建更新，核对真实返回 ID 与版本是否进入后续输入。对于嵌套来源，核对实际来源引用的连续性。

对于最终回答，`_final_basis_contains` 要求：最终结果依据哈希等于当前运行结果基准、上下文快照处于校验阶段、对应节点输出确实存在于校验工作记忆中且内容一致，然后还要由事实断言检查答案。

因此它证明的是“真实结果进入了下游或最终回答依据，且答案符合固定断言”，**不等于能够证明神经网络实际关注了某一片段，也不是对所有答案做了完整因果归因**。这条边界说清楚，比直接宣称“检测模型有没有使用工具结果”更准确。

## 面试追问与回答要点

**为什么不用固定 Workflow？**

小说写作请求的规模差异很大。已经给出全部事实的格式调整应直接回答；找一个对象只需单次检索；摘要后分支分析需要 DAG；写入还需人工介入。固定执行骨架负责可靠运行，单次请求决定实际能力图。18 条中零调用和单调用案例正是验证不要强迫小请求进入长流程。

**为什么还需要 LangGraph，自己写一个队列不行吗？**

依赖调度之外还有持久化检查点、人工中断和恢复语义。太初用官方 StateGraph 与 Send 承接固定执行骨架，动态任务图放在状态里。业务运行投影负责展示与审计，不能冒充框架执行检查点。

**“100%”会不会是模型自己判自己？**

这组模型输出是脚本控制的，目标是稳定回归工程行为。判分由确定性门禁、独立事实目录和真实执行证据完成；错误回答、缺数据流、错资源后态的负例会失败。它不是开放问答的独立模型盲测，不能外推真实模型业务成功率。

**脚本都给了答案，评测还有什么价值？**

因为要测试的是生产 Runtime 是否真正执行正确能力、绑定真实返回值、等待批准、保护资源、传播依赖并保留证据。脚本响应控制了模型随机性，使同一个工程问题能够复现。但它无法覆盖真实模型选择错误能力、生成低质量内容和语义漂移的概率，这部分需要真实模型赛道另测。

**18 条为什么不是越多越好？**

当前 18 条覆盖不同工程边界，便于逐条解释和排障。规模有限是事实，不能据此声称广泛泛化；后续可以补充真实请求与模型失败案例，但不能把尚未执行的扩展写成现有成绩。

**3 路并发有没有测过？**

产品默认上限是 3，源码通过图执行配置限制并发。当前 18 条中的并行相关合同主要检验依赖独立性，没有把“3 个节点时间区间实际重叠”作为这些案例的判分前提。性能提升、并发吞吐需用独立测量说明。

**怎么避免子 Agent 做了很多事，父 Agent 完全没用？**

通过显式输入绑定、产物引用、真实输入输出哈希与最终回答依据快照检查交接，再用最终语义断言检查回答。可以定位“结果未传过去”或“答案不包含要求结论”，但不会把这说成读取了模型内部注意力。

**这 9 类是不是完整的小说写作测试集？**

不是。它们是固定合同的产品展示分类，某些名字比实际验证范围宽。介绍时应举具体案例，例如“摘要分发后双分支汇总”“预览批准后精确应用”“创建 ID 驱动下一轮更新”，比泛称“全面覆盖小说写作”更有依据。
