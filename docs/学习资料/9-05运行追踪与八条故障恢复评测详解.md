# 运行追踪与八条故障恢复评测详解

本文面向准备介绍太初项目、回答 Agent 工程可靠性问题的开发者。读完应能解释：任务中断后从哪里继续，哪些动作可以复用，为什么正文已经写入却不能直接重试，八条恢复案例各自证明了什么，以及简历里的“零重复”有什么明确边界。

**核心判断：太初用 LangGraph 官方检查点保存执行位置，用完整能力结果避免重复调用，用副作用账本和真实资源对账处理写入不确定性；运行投影、调用追踪和模型回放提供观察证据。恢复的目标包括继续完成、保持待授权和在证据缺失时停止。**

实现核对基线为 2026 年 9 月 5 日的当前源码、测试、套件及当日只读查询得到的 Opik 结果。本文解释现有实现，不替代源码与测试契约，也不把夹具中的预期描述当作已发生的执行结果。

本文与[动态任务编排与十八条多步骤评测详解](9-05动态任务编排与十八条多步骤评测详解.md)配套阅读：前者讲正常执行路径与约束检查，本文沿异常发生后的状态接续展开。

## 一、先把简历中的一句话拆成四个可证明的命题

原表述是：

> 构建 8 条故障恢复回归用例，覆盖子图中断、人工授权、写后对账及检查点损坏等场景；测试中，可恢复场景的已成功节点重执行次数与重复副作用均为 0，检测到检查点损坏时停止恢复。

其中有四个命题，需要分别找证据。

| 命题 | 当前实现和证据 | 面试时应如何限定 |
|---|---|---|
| 有 8 条故障恢复案例 | 当前套件中有 8 条 `recovery_*` 案例，覆盖 7 类注入点；多次中断案例串联两个注入点 | 是 8 条确定性回归案例，不是随机故障组合的穷举 |
| 中断后能正确接续 | 6 条预期完成，1 条保持待授权，1 条检查点缺失后安全失败 | “符合恢复契约”不能改成“8 条业务任务全部恢复完成” |
| 已成功节点和副作用不重复 | 7 条案例检查计划一致及零重复投影；专项测试额外检查实际调用次数、完整产物与正文哈希 | 限定为已测试窗口，并区分完整成功结果与尚未完成的尝试 |
| 损坏检查点能停止恢复 | 当前第 29 条案例实际删除官方线程检查点，观察 `missing`（缺失）并停止 | 当前简历更准确的词是“检查点缺失”，不能扩写成所有损坏格式和跨版本迁移均验证通过 |

当前第 29 条的正式案例标识已是 `recovery_checkpoint_unavailable`，中文名为“官方 Checkpoint 缺失时安全停止”。配套夹具目录仍叫 `29_recovery_checkpoint_integrity_or_version`，这个路径名不表示当前执行器实现了任意损坏修订链回退。阅读时应以当前套件、执行路径及实际断言为准。

## 二、一次真实恢复的全貌

可以先用下面这条主线建立印象。这里的箭头表示职责衔接，不表示所有数据进入同一个存储事务。

```text
作者请求 → 当前会话的 LangGraph 线程 → 高层规划 → 动态能力执行图 → 结果校验
                       │                    │              │
                       │                    ├─ 只读工具/子 Agent → 完整结果提交到 Store
                       │                    └─ 写工具 → 副作用账本 → 修改真实资源
                       │                                         └─ 成功证据/对账
                       └─ Checkpointer 保存图状态、下一步和 interrupt

                           异常中断
                               ↓
                重建 Runtime，调用 recover_interrupted()
                               ↓
                校验归属 → 副作用 → 检查点 → 结果 → 上下文
                               ↓
       有待人工请求：保持等待 / 证据不足：停止 / 可以恢复：沿原线程接续
                               ↓
       业务投影、调用追踪、模型回放、恢复决策共同提供可阅读的运行证据
```

### 2.1 会话、业务运行和节点不是同一个标识

`conversation_id` 是长期会话标识，也是 LangGraph 的 `thread_id`。同一会话每次请求有自己的业务 `run_id`，用于关联计划、调用、预算与恢复证据。恢复不能新建一个请求代替旧请求，也不能把业务运行编号当作外层图线程。

还有两种容易混淆的“节点”。

| 名称 | 在太初中的含义 | 为什么影响“零重复”的理解 |
|---|---|---|
| 业务计划节点 | 比如读取结构、预览正文补丁、应用补丁；记录在动态计划和 `node_runs` 中 | 一条成功业务能力调用应能够复用其结果 |
| LangGraph 节点 | 例如 `plan`、`start_dag`、`execute_dag`、`verify` 和内部调度节点 | 恢复时框架可以重新进入未提交的节点函数，这不必然意味着再次调用业务工具 |

例如“工具已完成，但它的成功状态还没回到图状态”时，LangGraph 可能重新进入能力执行代码。执行器先查已经提交的能力结果，直接还原业务成功状态，而不是再请求一次工具。因此“零成功节点重执行”不能讲成“恢复时任何 Python 函数都只执行一次”。

外层图和恢复入口见 [Runtime 服务](../../src/taichu/application/general_agent/service.py) 的 `_build_graph()`、`_execute_run()`、`recover_interrupted()`；业务能力执行见 [动态执行器](../../src/taichu/application/general_agent/executor.py)。

### 2.2 五类持久证据各自负责什么

| 证据 | 主要内容与当前存储入口 | 负责什么，不能替代什么 |
|---|---|---|
| 官方检查点 | `MongoDBSaver` 保存图状态及待处理写入；应用组合根使用 `langgraph_checkpoints`、`langgraph_checkpoint_writes` | 决定执行位置、线程状态与人工中断；是恢复控制流的依据 |
| 业务运行投影 | `derived/general_agent_runs/<run_id>.json`；保存计划、节点、状态、最终回答和审计关联 | 供列表、监控与审计使用；与图状态冲突时不能反过来指挥图恢复 |
| 完整能力结果 | 官方 LangGraph `Store` 中按会话、运行构造 namespace，保存输出、来源、产物、身份和内容哈希 | 证明某次只读工具或子 Agent 已完整成功，供执行器复用；不处理写入是否生效的不确定性 |
| 副作用账本 | `derived/general_agent_effects/<run_id>.jsonl`；按事件追加准备、开始、成功、对账等状态 | 证明写操作身份和执行边界，驱动对账；不能代替真实 Markdown 或 MongoDB 业务事实 |
| 追踪与模型回放 | 调用 Trace 保存来源、父子调用和状态；`derived/llm_call_replays` 保存脱敏模型调用；上下文快照保存阶段输入 | 用于观察、解释、回放和评测；不能凭一条 Trace 成功或一份回答文本直接恢复图 |

“分层持久化”不是把同一份大 JSON 复制五遍。它解决的是不同问题：**下一步做什么、之前完成了什么、真实写入是否发生、当时看到了什么。**

应用的默认持久组件由 [启动组合根](../../src/taichu/main.py) 装配。具体实现见 [业务投影仓储](../../src/taichu/infrastructure/general_agent_runs/json_repository.py)、[能力结果仓储](../../src/taichu/infrastructure/general_agent_runs/capability_result_repository.py)、[副作用仓储](../../src/taichu/infrastructure/general_agent_runs/effect_repository.py)、[模型回放仓储](../../src/taichu/infrastructure/llm_replays/json_repository.py)。能力结果现在使用官方 Store，不应照着旧夹具中的 `result_index` 字样讲成仍维护独立 JSON 结果索引。

## 三、恢复机制为什么能避开三个常见错误

### 3.1 不把“服务重新启动”当作“重新发送用户请求”

应用启动时会调用 `recover_interrupted()`。它根据运行索引定位会话，再读取官方 `StateSnapshot`（图状态快照），查看状态中的业务运行、待处理的 `interrupt` 和下一步。

其关键判断是：

1. 官方图中已有人工中断：恢复展示该请求，保持等待，不越过作者决定。
2. 图已经结束：更新展示投影，不重新执行。
3. 业务投影明确取消：保持取消；显式失败和超时也不自动当作新任务重跑。
4. 图还有下一步：完成恢复预检，再以原 `thread_id` 接续。
5. 原活动运行已经找不到可用检查点：记录停止原因，不用业务投影重新拼一张图冒充恢复。

正常接续使用官方图状态；人工继续传入 `Command(resume=...)`，让原 `interrupt()` 消费本次回答。作者批准写入时仍需匹配原请求类型、请求标识及确定输入。

### 3.2 不把“结果存在”当作“任何调用都可以复用”

完整结果的身份包括会话与运行归属、计划修订、业务节点、尝试标识、能力类型与名称、输入哈希、处理器身份，以及输入输出 Schema 的哈希。结果本身也校验语义内容和完整记录的哈希。

因此复用的是“这个身份对应的完整结果”，不是“找一条名称相同的工具输出”。参数、实现或契约不一致时不能混用。一次没有提交完整结果的子 Agent 尝试，则允许在原图中重新执行；半成品不会被登记为可复用结果。

见 [结果身份与严格模型](../../src/taichu/application/contracts/general_agent_capability_results.py) 和执行器的 `_result_identity()`、`_completed_result()`、`_execute_node()`。

### 3.3 不把“没保存成功状态”当作“肯定没写入”

写工具的典型顺序是：

```text
冻结输入、授权与资源范围
    → PREPARED（已准备）
    → STARTED（写入将开始）
    → 工具修改真实资源
    → RESOURCE_WRITE_APPLIED 故障窗口
    → SUCCEEDED（成功证据落盘）
```

最危险的窗口在“真实资源已变”与“成功证据落盘”之间。只看检查点，执行器可能以为写入没完成；直接重试追加正文会把相同文本写两遍。

太初先按稳定 `effect_id` 查账本。成功或已对账的操作直接复用；处于已开始状态的操作先调用该工具的 `reconcile()`（对账接口）。对于正文补丁，它读取当前 Markdown，比较三个哈希：

| 当前正文与哪个版本相同 | 对账判断 | 后续动作 |
|---|---|---|
| 与授权预览的预期正文相同 | 已生效 | 追加 `RECONCILED`（已对账）证据，返回当前内容，不再次写入 |
| 与写前正文相同 | 未生效 | 允许在原确定输入与权限约束下安全重试 |
| 两者都不同 | 不确定 | 保留证据并进入人工核对，不猜测，也不覆盖作者的新修改 |

恢复预检顺序固定为 **owner（归属）→ Effect（副作用）→ Checkpoint（检查点）→ Result（结果）→ Context（上下文）**。已经明确未知或待人工处理的副作用优先阻止自动恢复，有一份“看起来成功”的能力结果也不能越过这个边界。

见 [恢复协调器](../../src/taichu/application/general_agent/recovery.py) 的 `prepare()`、[写工具执行分支](../../src/taichu/application/general_agent/executor.py) 的 `_execute_write_tool()`、[正文补丁写入及对账](../../src/taichu/application/tools/apply_manuscript_patch.py)。

## 四、八条案例究竟怎样执行

### 4.1 先认清评测使用的是真实 Runtime 加脚本模型

这 8 条在当前套件中只适用于 `synthetic`（确定性合成）轨道。编排计划和模型回答由严格脚本提供，实际恢复则运行生产的 Runtime、LangGraph 和注册能力，正文写入发生在隔离夹具中。合成轨道用于隔离模型随机性，让持久化与恢复逻辑可以稳定回归，不代表模型理解任意写作请求的质量。

外层案例执行器先消费套件的脚本交互，再根据 `fault_plan_ref` 运行真正的恢复 Harness（故障驱动器）。因此仅看 `suite.json` 中某些 `nodes=[]` 的脚本，会误以为恢复测试没有业务节点。真正的业务计划在 `SyntheticRecoveryHarness._execution_plan()` 中构造，最后采用恢复运行作为 `observed_run`（被评测运行）。外层案例可以产生准备运行；**同一条恢复过程自身始终保持同一 `run_id`、同一会话、同一计划。**

另一个重要限定是：当前注入异常 `InjectedProcessTermination` 继承 `RuntimeError`。Runtime 和执行器显式重新抛出它，避免普通失败分支把运行改成已终止；Harness 捕获异常、关闭 Runtime，再构造新 Runtime 和部分仓储对象。这里没有调用操作系统去杀掉 Python 进程，内层恢复会复用数据库检查点对象、图 Store 以及脚本模型对象。完整合成环境使用真实 MongoDB 检查点，专项单元测试也会使用内存实现；不能笼统声称所有测试都验证了 OS 强杀、机器掉电或数据库重启。

故障计划先绑定实际运行身份，再把已触发的序号持久保存。重建后会读这个触发记录，已经发生的故障不会无限重复。多次中断要求依次触发 `1、2`，不允许跳号、错归属或静默漏触发。见 [故障注入协议](../../src/taichu/application/general_agent/faults.py)、[持久故障计划与触发仓储](../../src/taichu/application/evaluations/general_agent_benchmark/faults.py)、[通用恢复 Harness](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/recovery_harness.py)。

## 五、案例 22：规划已经生成，但第一个能力还没执行

**问题场景。** 作者提出一个需要读取小说信息的请求，模型已经花费一次调用生成计划；如果服务此时中断，重新规划可能产生不同 DAG，也会浪费原规划成本。

**实际输入和计划。** 主套件的请求原文是“请在密封评测场景中完成‘规划后执行前恢复’，并只依据当前案例输入给出结果。”对应 Harness 构造一个 `recovery_read` 业务节点，调用 `get_novel_structure`（读取小说结构），然后进入编排校验。专项测试使用“读取结构后给我一条建议”，原理相同。

**断点为何放在这里。** `PLAN_CREATED` 并非写完业务 JSON 就立即触发，而是放在 `start_dag` 节点入口。进入该节点说明上一个 LangGraph super-step（一次图调度提交批次）中的规划状态已经由官方检查点提交。若在框架持久化之前就宣称“规划已保存”，恢复时仍可能重新进入规划节点。

**中断后留下什么。** 原计划、原运行与会话身份已经存在，业务运行处于执行态；尚无业务能力节点的执行结果。专项测试断言中断快照的 `node_runs == []`。

**恢复路径。** 重建后调用 `recover_interrupted()`，检查原线程，沿 `start_dag` 进入执行图。读取结构发生一次，随后完成校验；规划模型不再调用。

**验证。** `test_runtime.py` 中使用 `fault_after_plan` 的专项测试断言：故障只触发一次、前后计划哈希一致、规划调用一次、结构读取成功 Trace 一条、最终业务节点成功且运行完成。主套件另要求 `a22_artifact` 产物契约与 `a22_recovery` 恢复复用断言通过。

**如果这个机制失效。** 后果可能是重新规划、原计划丢失或新增一条重复任务。此案例重点是“复用规划”，因为断点前还没有成功业务能力，不能把它单独当成“任何已成功工具都不重跑”的充分证据。

阅读：[案例夹具](../../tests/fixtures/evaluations/general_writing_agent_benchmark/fixtures/core_novel/recovery/22_recovery_after_plan_before_execution/fault-plan.json)、[Runtime 专项测试](../../tests/unit/application/general_agent/test_runtime.py)。

## 六、案例 23：工具结果已经提交，但还没有成为节点成功状态

**问题场景。** 工具已经读出结构，结果成功写入持久结果仓储；但父执行图还没收到这个结果，程序就中断了。恢复若只看图中的“未完成”，会再次请求同一个工具。

**实际执行。** 主套件仍是单个 `get_novel_structure` 节点。执行器拿到完整 envelope（包含输出与证据的调用结果）后，先构造并提交 `CapabilityResultRecord`，再触发 `CAPABILITY_RESULT_COMMITTED`；故障发生在 `_successful_capability_result()` 将结果投影为业务节点成功状态之前。

**中断后留下什么。** 完整结果已经存在于官方 Store 的结果 namespace，包含输出、来源、产物、内容哈希和完整调用身份。图可能仍需重新进入能力执行函数，但不需要再请求工具。

**恢复路径。** 执行器按相同身份查询 `get_completed()`，匹配后直接返回成功业务节点；输出来自原结果，且 `reconciliation_reason` 中保存复用的结果标识与哈希。

**问题场景。** 只测一次重启，容易遗漏“第一次恢复留下的状态，能否继续支撑第二次恢复”。例如重复生成计划、丢失已触发故障的标记，或给相同写操作生成新身份。

## 十三、“零重复”究竟怎样计算，为什么还要看专项测试

### 13.1 主套件中的确定性断言

前七条通过 `RecoveryReuseObservation`（恢复复用观察）向 Oracle（确定性判定器）提供证据。判定器要求：前后计划哈希相同；成功节点重执行计数不超过 0；重复副作用计数为 0；没有被标记为重新尝试的成功结果。它还交叉检查恢复后计划哈希与最终案例观察一致。

当前两个计数的实现是：

```text
successful_node_reexecutions
  = 恢复决策中 retried_capability_result_ids 去重后的数量

duplicate_side_effects
  = 对每个 effect_id，统计不同 attempt_id 数量超出 1 的部分，再求和
```

见 [恢复观察投影](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/synthetic_recovery_harness.py) 和 [恢复复用 Oracle](../../src/taichu/application/evaluations/general_agent_benchmark/oracles.py) 的 `_recovery_reuse()`。

### 13.2 两个零不是覆盖所有外部行为的万能证明

第一个计数依赖恢复审计记录；当前协调器准备恢复时把已存在结果列为复用结果，并初始化空的重试成功结果列表。它不是独立拦截每次底层调用的全局探针。第二个计数按身份统计，同一尝试身份内如果错误重复写入，单靠该计数未必识别得到。

因此本项目还用专项测试直接检查：调用计数器、成功 Trace 条数、完整结果条数、正文哈希、真实写入次数，以及 `PREPARED → STARTED → RECONCILED` 的账本链。解释“为什么可信”时，应同时说清这两层证据，不能只说“仪表盘显示 0”。

案例 22 在断点前还没有成功能力，案例 25 本来就没有获准写入。它们的零值有清楚的场景原因；最强的成功结果复用证据来自案例 23，最强的防重复写入证据来自案例 26 和 28。案例 24 则证明未完成尝试允许重做，不能追求所有尝试总数都等于 1。

### 13.3 不承诺分布式系统意义的任意故障“恰好一次”

`effect_id` 与 `attempt_id` 根据运行、计划修订和节点生成稳定身份；账本追加会 `flush` 并 `fsync`，正文工具提供对账接口。这些机制保证的是已覆盖场景中的可恢复行为。

当前材料不能证明任意工具、任意并发进程、数据库与文件系统同时故障、断电以及外部服务不可查询结果时，都能严格实现端到端 exactly-once（恰好执行一次）。这里也没有把 Markdown 写入和 MongoDB 检查点放进一个跨资源原子事务。对账返回不确定时主动停下来，是实现的一部分，而不是对“零重复”承诺的例外掩饰。

### 14.1 嵌套 Trace 与运行回放的职责

Opik 评测案例、恢复 Harness、模型轮次，以及带观察包装的工具和专业子 Agent 调用具有追踪入口。`@opik.track()` 让当前调用栈中的追踪形成父子关系，元数据携带案例、故障计划、能力名称和调用标识，便于从一个失败结果追到相关调用。

但不能仅凭“项目中这些函数有装饰器”就说每次运行一定有全部细粒度 Span。当前恢复 Harness 重建依赖时把 `interaction_observer` 设为 `None`，不会经过评测工厂中依赖该观察器的工具/子 Agent 包装层。本次还只读抽查了正式实验中的写后恢复、子 Agent 恢复 Trace，确实保留恢复子图与模型 Span，但没有独立工具/子 Agent Span。其输出中的 `invocation_count=0` 反映观察投影范围，不能推导实际没有执行工具；本地调用证据仍由真实注册表记录，专项测试中的写入/对账计数也有独立验证。

此外，断点附近尚未完整提交的调用可能没有完整回放记录。回放用于查看已经保存的证据，不等于重新执行所有外部操作，也不承担恢复调度职责。

追踪入口：[案例执行器](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/synthetic_environment.py)、[恢复 Harness](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/recovery_harness.py)、[模型与能力观察包装](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/synthetic_runtime.py)、[评测 Runtime 工厂](../../src/taichu/infrastructure/evaluations/general_agent_benchmark/runtime_factory.py)。

## 十六、面试中可以怎样解释

### 16.1 一段可复述的项目说明

> 太初的多步骤写作任务既有只读检索，也有需要作者授权的正文写入。我把恢复拆成执行状态、完成结果和副作用三件事：LangGraph 检查点按会话线程接续原图，完整能力结果避免已经成功的工具再次调用，写工具则用副作用账本和正文哈希对账处理“写入成功但成功状态没记录”的窗口。用 8 条确定性故障恢复案例覆盖规划、结果提交、子 Agent、授权、写后、校验、连续中断和检查点缺失。正确终态包含完成、保持待授权与安全停止；在已测试窗口中检查成功结果不重复调用、已发生写入不重复应用，并用 Trace、账本和真实资源断言核实。

### 16.2 典型追问与回答要点

**问：为什么有了 LangGraph Checkpoint，还要能力结果仓储和副作用账本？**

检查点解决框架执行位置；能力调用和框架状态提交之间还有间隙。只读工具结果完整提交后可以复用，写入则还可能先修改真实资源再提交成功状态，所以需要独立对账。三者分别覆盖不同提交边界。

**问：如果数据库里写了成功，文件里没成功怎么办？**

先明确是哪份“成功”：Trace、业务投影、检查点和写入账本不是同一事实。正文事实仍由当前 Markdown 决定；写工具对账读取资源，用写前与预期哈希判断。如果资源既非写前也非预期，进入人工核对。不能只凭一个展示字段就继续覆盖。

**问：你们是不是所有节点恰好执行一次？**

不是这个口径。框架可能重入未完成节点，子 Agent 未完成尝试也允许重做。保护的是完整成功结果不被重复请求，以及能够证明已经生效的写操作不再次应用。当前零值来自回归计数和专项资源断言，不承诺任意分布式故障下的全局恰好一次。

**问：8 条是实际杀进程吗？**

当前是专用异常注入、关闭并重建 Runtime 的确定性测试，不是操作系统强杀。完整合成环境使用真实 MongoDB 检查点，部分内层依赖会复用；专项测试还使用内存检查点。应明确介绍已经验证的运行时恢复窗口，不能把它扩大成机器掉电测试。

**问：为什么检查点缺失时不拿运行 JSON 接着跑？**

业务 JSON 是投影，无法证明框架下一个节点、待处理写入和 interrupt 的一致位置。没有检查点还自动拼图，可能重复执行副作用。正确做法是停止并保留证据，由后续明确操作处理，而不是把“猜测继续”叫恢复。

**问：Opik 的 100% 是模型给自己打分吗？**

这组恢复案例使用确定性契约判定，核对终态、计划、恢复观察、预算和证据；不靠模型判断“自己恢复得不错”。Opik 负责组织实验和显示结果。合成轨道中的模型输出由脚本固定，所以分数证明工程契约在固定场景下成立，不证明写作内容质量。

**问：哪个案例最能体现你做了框架之外的工程工作？**

可以先讲案例 26：在真实写入与成功日志之间中断，账本只有开始状态，恢复后读正文哈希确认已生效，只追加对账证据而不再写。再用案例 23 说明另一种提交窗口：工具完整结果已保存但父节点还未成功，重入执行代码时复用原结果。最后补上案例 25，说明自动恢复必须尊重作者尚未作出的决定。

### 16.3 与当前证据一致的简历写法

> **运行追踪与故障恢复：** 基于 LangGraph Checkpoint、完整能力结果与副作用账本构建同线程恢复机制，支持运行证据与模型调用回放；构建 8 条确定性故障恢复回归用例，覆盖结果提交、子 Agent 中断、人工授权、写后对账及连续中断等窗口，测试中可恢复场景的成功节点重执行与重复副作用计数均为 0，官方检查点缺失时安全停止。

这段话中的“计数”仍需配合本文的专项测试说明。面试时掌握“检查点决定继续位置，结果证明已完成，账本加资源对账证明写入是否生效”这条主线，再用 23、25、26 三个具体窗口展开，就能把简历中的指标解释成可核验的工程设计。
