# 知识沉淀智能体（Agent）效果评估方案

> 更新日期：2026-07-18
> 资料状态：方案已确认，尚未实现
> 已选路线：确定性指标与 LLM 裁判结合
> 适用范围：正文知识沉淀 Agent 的单章任务、批量章节任务、历史任务回放与质量回归

本文给出一套可以直接交给 Codex 实施的效果评估设计。它描述目标架构、数据契约、评分口径、接口、页面、测试和实施顺序，但不表示相关代码已经落地。实现事实仍以当前代码、AGENTS.md、DESIGN.md 和 project_assets/readme.md 为准。

## 1. 结论

知识沉淀 Agent 的效果评估采用双层机制：

1. 确定性评估层负责范围校验、候选卡匹配、Precision、Recall、F1、结构字段、证据定位、负样本和批量重复等可重复指标。
2. LLM 裁判层只评估已经确定性匹配成功的卡片，判断摘要、来源说明和类型专属自由文本是否语义正确、是否漏掉关键事实、是否包含无来源断言或事实矛盾。
3. LLM 裁判不得改变候选匹配关系，不得补造金标，不得覆盖确定性指标。
4. 任务启动后的 LLM 调用不可用、超时或输出非法 JSON 时，评估仍保留确定性结果，并以“语义裁判未完成”结束；启动前未配置裁判模型则明确拒绝方案 B，不静默降级。
5. 前端可以展示透明的综合参考分，但必须同时展示各维度原始指标、裁判覆盖率和风险项，不能只展示一个总分。

整体链路如下：

~~~text
用户选择已注册评测集和历史任务
  → 校验任务范围、正文哈希和评测集完整性
  → 后端原子冻结任务输出、评测集、正文和评分口径
  → 确定性匹配候选卡
  → 计算候选、结构、证据和负样本指标
  → 为已匹配卡片构建最小证据包
  → LLM 裁判分批评估自由文本
  → 聚合单卡、单类型、单任务和多任务指标
  → 原子保存评估记录
  → 前端展示指标、差异、裁判理由和审计记录
~~~

## 2. 已核对的当前实现

### 2.1 运行能力

- 正文知识沉淀 Agent 的插件名称是 knowledge_extraction。
- 当前单章图包含读取、分段、通用抽取、mention 规范化、实体聚合、质量闸门、类型分发、三个专家节点、候选合并、Schema 校验、冲突检查、已有知识匹配、审核项生成和 JSON 写入。
- 实际调用模型的是 GeneralExtractionNode、CharacterExpertNode、EntityExpertNode 和 EventRuleExpertNode。仓库没有 LAM 节点概念，产品与文档统一使用“LLM 节点”。
- 批量任务由应用服务额外编排，不是插件输入本身。当前数字 5 表示章节分支最大并发数 max_concurrency=5，不是最多选择 5 章，也不是最多生成 5 张候选卡。
- 批量任务可能出现 status=completed 但 failed_chapter_count 大于 0。评估资格不能只检查 completed。
- 当前请求中的 model_name 会进入运行记录，但 LLMContract.complete 不接收模型参数，底层聊天模型在应用启动时已经创建。因此 model_name 目前不能单独证明真实调用了哪个模型；评估实施必须先收敛真实模型来源记录，不能用一个仅用于展示的字符串判断是否自评。

### 2.2 可评估输出

评估以运行结束时生成的候选卡为对象：

~~~text
AgentRun.review_items[*].suggested_card
~~~

不得使用以下对象替代：

- 不使用作者确认后写入知识库的正式卡，因为其中可能包含作者编辑。
- 不重新运行 Agent 获取“当前输出”，否则无法评估历史任务。
- 不按数组位置匹配金标。
- 不使用 review_item_id 匹配金标，因为它只在单次运行内有意义。
- 不按专家目录名与节点名匹配，因为当前金标的 worldview_expert 与运行节点的类型划分并不完全一致。

所有聚合和匹配以 knowledge_type 为准。支持的类型为：

~~~text
character
realm
technique
location
faction
item
rule
event
~~~

### 2.3 现有评测资料

现有金标位于：

~~~text
tests/fixtures/evaluations/taichu_knowledge_eval_first5_three_experts/
~~~

它包含：

- 五个单章场景。
- 一个前五章批量场景。
- 三个专家目录和八种知识类型。
- 严格知识卡。
- evidence_index.json。
- ignored_candidates.json。
- Schema 快照。
- 全文件 SHA-256 清单。

当前 manifest 记录的期望卡数量依次为：第 1 章 13 张、第 2 章 11 张、第 3 章 18 张、第 4 章 27 张、第 5 章 25 张、前五章批量 67 张。数据集加载测试必须以这些数量校验没有重复读取。

当前没有评估器、评估 API 或页面消费这些文件。

现有资料可以作为首个数据集的内容基础，但不能直接标记为可运行金标，原因如下：

- cards 文件包含 id、created_at、updated_at 等实际候选没有的系统字段。
- 实际候选包含 entity_group_id、evidence_excerpt、evidence_excerpts 等评测专用或运行辅助字段。
- evidence_index 中部分内容是概述或转述，不是可在 Markdown 中定位的精确原文。
- manifest 尚未提供统一 case 清单、lifecycle、正文哈希和字段评估规则。

实现阶段必须先执行“金标准入改造”，通过校验后才能把数据集 lifecycle 设为 confirmed。

## 3. 目标与非目标

### 3.1 目标

- 用户可以在任务监控下进入“知识沉淀 Agent 效果评估”。
- 用户可以选择一个已确认评测集，并勾选一个或多个历史任务。
- 系统自动根据章节范围找到对应期望输出，不要求浏览器读取本地 JSON。
- 系统给出候选识别、字段质量、语义质量、证据质量和负样本质量。
- 系统可以展示漏提取、多提取、字段差异、语义问题、证据问题和裁判分歧。
- 每次评估都保存实际输出、期望输出、参与正文快照与哈希、真实模型身份、Prompt 契约、裁判调用和评分规则，保证可追溯。
- 同一评测集可以比较不同模型、Prompt 和 workflow 调整后的历史任务。
- 评估结果为后续复杂 Agent 的评估能力提供清晰扩展边界。

### 3.2 非目标

首轮不做：

- 不让 LLM 裁判自动修正候选卡。
- 不把评估结果写入 MongoDB。
- 不把评估节点插入原知识沉淀 LangGraph。
- 不依赖 LangSmith 或第三方评估平台。
- 不提供任意绝对路径读取能力。
- 不做跨小说、多租户或在线评测集市场。
- 不把作者确认率直接当作模型准确率。
- 不用语义裁判决定实体是否为同一个对象。
- 不用复杂图表替代可核对的列表和差异。

## 4. 强制设计决策

| 决策 | 结论 |
|---|---|
| 评估实际输出 | 读取运行记录中的 suggested_card，并在创建评估时冻结快照 |

| 状态表达 | 中文文字、图标和边框共同表达，不只靠颜色 |
| 组件依赖 | 优先复用本地组件和现有 Base UI，不新增第三方依赖 |

## 5. 分层与职责

### 5.1 应用层

应用层负责：

- 评估任务编排。
- 评测集准入校验。
- 运行资格判断。
- 候选规范化与一对一匹配。
- 指标计算和综合分聚合。
- LLM 裁判 Prompt 构建、输出校验和一致性处理。
- 评估状态与生命周期转换。

评估模型属于 Agent 应用能力，不新增到技术无关的 domain 中，统一放在：

~~~text

~~~

### 5.2 应用契约

新增 Protocol：

~~~text
src/taichu/application/contracts/agent_run_repository.py
src/taichu/application/contracts/evaluation_dataset_repository.py
src/taichu/application/contracts/evaluation_result_repository.py
src/taichu/application/contracts/evaluation_judge.py
~~~

职责：

- AgentRunRepository：定义 write_run、get_run、delete_run、list_runs、find_run_for_candidate，覆盖现有运行仓库全部行为。

- EvaluationResultRepository：原子写入、读取、分页和软删除评估记录。

现有 workflow.py 和 KnowledgeExtractionService 都直接依赖 JsonAgentRunStore。实施时必须让 JsonAgentRunStore 实现 AgentRunRepository，并同步把 workflow、KnowledgeExtractionService 和新评估服务的具体类型依赖全部替换为 Protocol，不能留下新旧两套跨层耦合。

当前 AgentRun 位于 domain/models/agent_run.py，但 Agent 属于应用层协议，已经不符合“domain 不得依赖 Agent”的项目规则。本任务既然需要扩展运行来源字段，就必须同时完成边界收敛：

- 把 AgentRun、AgentReviewItem、节点、调用和指标模型迁移到 src/taichu/application/agents/models/agent_run.py。
- 更新 API、应用服务、workflow、事件中心、基础设施仓库和测试的 import。
- 从 domain/models/__init__.py 移除 Agent 模型导出，并删除旧 domain/models/agent_run.py。
- JSON 字段保持不变，由 JsonAgentRunStore 的兼容加载器继续读取历史运行。

## 6. 数据来源、生命周期与不可变性

### 6.1 评测集

评测集是人工校准资料，必须包含 lifecycle：

- draft：仍在补卡、补证据或校准规则，不允许参与正式评估。
- confirmed：准入校验通过，允许在页面选择。
- rejected：废弃，默认列表和普通筛选不显示。

评测集不写入 project_assets，不写入 MongoDB。

### 6.2 评估记录

评估记录是派生审计数据，同时具有：

- lifecycle：draft、confirmed、rejected。
- status：pending、running、completed、completed_with_warnings、failed。
- phase：queued、deterministic、judging、aggregating、finished。

状态转换是显式状态机，仓库层和服务层都必须拒绝表外转换：

| 当前状态与阶段 | 允许的下一状态与阶段 | 触发条件 |
|---|---|---|
| pending / queued | running / deterministic | 后台执行器成功领取任务 |
| pending / queued | failed / finished | 领取失败或确认进程已经中断 |
| running / deterministic | running / judging | 确定性结果完整且启用裁判 |
| running / deterministic | running / aggregating | 确定性结果完整且未启用裁判 |
| running / deterministic | failed / finished | 快照损坏或确定性计算失败 |
| running / judging | running / aggregating | 裁判结束，包括允许降级的部分失败 |
| running / judging | failed / finished | 无法读取冻结输入或持久化中间结果 |
| running / aggregating | completed / finished | 所有要求的结果完整 |
| running / aggregating | completed_with_warnings / finished | 确定性结果完整，但裁判不完整或存在可降级警告 |
| running / aggregating | failed / finished | 聚合或持久化失败，无法形成可靠报告 |

- 创建任务成功发布快照后固定为 lifecycle=draft、status=pending、phase=queued。
- completed、completed_with_warnings、failed 都是计算终态；计算字段和 status 不可再覆盖。
- failed 只用于无法形成可靠确定性报告；单纯裁判失败必须落为 completed_with_warnings。
- lifecycle=draft 仅在 status 为 completed 或 completed_with_warnings 时允许变为 confirmed。
- lifecycle=draft 或 confirmed 仅在计算终态时允许变为 rejected；pending 和 running 不提供删除或取消。
- rejected 不允许恢复；若要再次评估必须创建新记录。
- 用户确认或废弃报告只改变 lifecycle 和 updated_at，不重算结果。
- 任何非法转换返回 409 和 EVALUATION_INVALID_TRANSITION。

### 6.3 原始候选快照

当前普通确认直接使用 suggested_card 写入知识仓库；“编辑后确认”使用临时 merged_payload 写入知识仓库。两条路径都不会改写运行记录中的 suggested_card；_mark_confirmed 只更新候选状态、作者动作、创建或更新知识卡 ID 和时间。因此 suggested_card 已经是可用于历史评估的 Agent 输出。

评估服务仍必须在创建任务时冻结一份实际候选快照，原因是原运行记录可以被用户删除，未来代码也可能改变审核行为。

规则：

- 实际输入固定读取 AgentRun.review_items[*].suggested_card。
- candidate_status、author_action、created_knowledge_card_id 和 updated_knowledge_card_id 不参与模型内容评分。
- 评估记录保存规范化前后的实际候选、run_snapshot_hash 和冻结时间。
- 评估执行期间不再次读取候选以覆盖快照。
- 删除或修改原运行记录不影响既有评估回放。
- 不新增 agent_output_card 等与现有 suggested_card 职责重复的字段。

### 6.4 正文快照

新增逐章来源摘要：

~~~text
AgentRunScope.chapter_content_hashes: dict[str, str]
~~~

新运行的单章和批量任务都必须保存每章 Markdown 的 SHA-256。历史兼容规则固定为：

- chapter_content_hashes 非空时直接使用。
- 旧单章运行缺少新字段但 scope.content_hash 非空时，映射为 {scope.chapter_id: scope.content_hash}，仍可完成来源校验。
- 旧批量运行缺少逐章哈希时标记 source_verification=unverified，只能降级诊断。
- 正文哈希明确不一致时标记 source_verification=mismatch，不启动语义裁判。
- 旧 content_hash 只为历史单章解析保留，兼容理由必须写入代码注释和测试。

评估结果还要保存：

- run_snapshot_hash。
- dataset_checksum。
- case_checksum。
- dataset manifest 快照。
- actual_cards_snapshot。
- expected_cards_snapshot。
- evaluation_rules 快照。
- source_evidence 快照。
- negative_cases 快照。
- metric profile 的实际参数快照。
- judge contract 的 Prompt 模板、prompt_contract_id、输出 JSON Schema 与哈希快照；未启用裁判时明确记录 enabled=false。
- 参与评估的章节 Markdown 内容与哈希快照。
- 实际发送给裁判的原文窗口和输入哈希。
- source_chapter_hashes。
- 匹配关系和差异结果。

因此即使原任务、评测集或当前正文后来被删除或修改，历史评估仍可完整回放。仅保存 checksum 而不保存当时输入内容，不满足本方案的可追溯要求。

## 7. 评测集契约

### 7.1 目录

一个评测集采用：

~~~text
tests/fixtures/evaluations/{dataset_id}/
├── manifest.json
├── _metadata/
│   ├── schema_snapshot.json
│   └── checksums.sha256.json
├── single_chapter/
│   └── chapter_001/
│       ├── expected_cards.json
│       ├── evaluation_rules.json
│       ├── source_evidence.json
│       └── negative_cases.json
└── batch_001_005/
    ├── expected_cards.json
    ├── evaluation_rules.json
    ├── source_evidence.json
    └── negative_cases.json
~~~

现有三个专家目录可以继续作为人工维护资料，但运行时加载器只能读取 manifest 明确列出的聚合文件，不能递归扫描 cards.json 和逐卡文件，否则会重复计数。

### 7.2 manifest 示例

~~~json
{
  "dataset_id": "taichu_knowledge_eval_first5_three_experts",
  "label": "太初前五章知识抽取评测集",
  "lifecycle": "confirmed",
  "agent_name": "knowledge_extraction",
  "schema_snapshot_path": "_metadata/schema_snapshot.json",
  "checksum_manifest_path": "_metadata/checksums.sha256.json",
  "cases": [
    {
      "case_id": "chapter_001",
      "scope_type": "chapter",
      "chapter_ids": ["chapter-f2a0007303a74f769e1609124c30da6b"],
      "source_chapter_hashes": {
        "chapter-f2a0007303a74f769e1609124c30da6b": "sha256..."
      },
      "expected_cards_path": "single_chapter/chapter_001/expected_cards.json",
      "evaluation_rules_path": "single_chapter/chapter_001/evaluation_rules.json",
      "source_evidence_path": "single_chapter/chapter_001/source_evidence.json",
      "negative_cases_path": "single_chapter/chapter_001/negative_cases.json"
    }
  ]
}
~~~

字段用于机器兼容或可复现时才保留。数据集变更以 checksum 识别，不增加“第几版”一类文档性字段。

需求中的“期望输出由 JSON 路径提供”具体落为 manifest 内的受控相对路径：数据维护者登记 expected_cards_path 等路径，浏览器只提交 dataset_id，后端解析并校验路径。这样既保留文件式金标，又不向前端开放任意本机文件读取。

### 7.3 evaluation_rules

每张期望卡至少包含：

- expected_card_id。
- knowledge_type。
- accepted_names。
- exact_fields。
- set_fields。
- semantic_fields。
- expected_claims。
- source_quote_ids。

expected_claims 示例：

~~~json
{
  "claim_id": "qin_soul_transfer",
  "field": "summary",
  "importance": "critical",
  "description": "秦浩轩能让灵魂在本体与五彩小蛇之间转移",
  "source_quote_ids": ["quote_ch001_003"]
}
~~~

accepted_names 用于处理事件、规则等生成式名称差异。它必须人工确认，不能由评估时的 LLM 临时扩充。

### 7.4 source_evidence

每条证据必须是正文原文，不是摘要：

~~~json
{
  "quote_id": "quote_ch001_003",
  "chapter_id": "chapter-f2a0007303a74f769e1609124c30da6b",
  "text": "正文中的连续原文",
  "start_offset": 1200,
  "end_offset": 1260,
  "source_hash": "sha256..."
}
~~~

偏移用于快速定位，最终仍需用 text 和 source_hash 复核。正文变化后偏移失效时，数据集不得继续 confirmed。

### 7.5 negative_cases

负样本描述“不应被建卡”的稳定对象或表达：

~~~json
{
  "negative_case_id": "generic_youths",
  "knowledge_type": "character",
  "accepted_names": ["几个少年", "围观少年", "少年们"],
  "reason": "泛称群体，无稳定专名",
  "source_quote_ids": ["quote_ch001_010"]
}
~~~

现有 ignored_candidates.json 可以生成初稿，但必须人工确认后转成此契约。

### 7.6 数据集准入校验

confirmed 数据集必须全部通过：

- 所有路径 resolve 后仍位于评测根目录。
- checksum 清单与实际文件一致。
- case_id、expected_card_id、claim_id、quote_id 唯一。
- dataset_id、case_id 和 chapter_id 满足白名单格式，且作为快照文件键时不存在规范化冲突或保留设备名。
- scope_type 只能为 chapter 或 chapter_batch。
- chapter_ids 与正文清单一致。
- source_chapter_hashes 与当前 Markdown 一致。
- 类型属于八种允许类型。
- 同类型 accepted_names 不冲突。
- 每张卡至少有一个可定位原文证据。
- 每个 critical claim 至少关联一个 source_quote_id。
- expected_cards 能通过当前知识卡 Schema 的适用字段校验。
- 聚合卡文件不存在重复卡。
- lifecycle 为 confirmed。

任何一项失败时，数据集只能以 draft 显示，不能开始正式评估。

## 8. 任务资格与 case 映射

### 8.1 case 映射

单章任务：

~~~text
scope_type == chapter
并且 run.scope.chapter_id == case.chapter_ids[0]
~~~

批量任务：

~~~text
scope_type == chapter_batch
并且 set(run.scope.chapter_ids) == set(case.chapter_ids)
~~~

章节顺序不参与 case 身份，但保存并展示实际顺序。

### 8.2 资格等级

每个历史任务分为：

- 完整可评估：运行完整、无失败章节、范围匹配、正文哈希一致、suggested_card 可冻结，且首轮所有应评审核项均为 create_card。
- 降级可诊断：可以计算部分指标，但缺少正文哈希、存在失败分支或含 update_card、conflict、ignore。
- 不可评估：无匹配 case、数据集损坏、候选无法读取或正文哈希明确不一致。

内部 eligibility_level 固定为 full、diagnostic、ineligible。full 和 diagnostic 都允许被选择并创建报告，ineligible 禁止选择：

- diagnostic 只运行能够成立的确定性匹配和差异，不进入 LLM 裁判，不生成单任务或聚合综合分。
- 同一请求混合 full 与 diagnostic 时，聚合可比较指标只统计 full；diagnostic 单独列在诊断区，不能悄悄并入分母。
- 只选择 diagnostic 也可以创建诊断报告，但 judge_card_count=0、overall_quality_score=null。
- 请求中只要包含 diagnostic，最终 status 至少为 completed_with_warnings，并保存逐任务降级原因。
- preview 的 can_create 在所有所选任务均为 full 或 diagnostic、输入可冻结且裁判配置条件满足时为 true；只要包含 ineligible 或其他阻塞错误就为 false。

## 9. 确定性匹配

### 9.1 规范化

名称与别名规范化规则固定为：

- Unicode NFKC。
- 去除首尾和内部空白。
- 英文 casefold。
- 统一常见全角标点。
- 不做拼音转换。
- 不删除具有身份意义的数字或称号。

缺失字段与 null 在字段比较时统一为空值，但在原始快照中保留原貌。

### 9.2 匹配优先级

只在 knowledge_type 相同的集合内建立边：

1. 规范化 name 完全相同：权重 100。
2. 实际 name 命中期望 accepted_names：权重 95。
3. 双方 name 与 aliases 交叉命中：权重 90。

按权重从高到低执行稳定的一对一匹配。若同一权重存在多解或一个身份键指向多张期望卡，标记 ambiguous，不得贪心占用。

模糊字符串和 LLM 可以生成“可能匹配”提示，但不得把提示计入 TP。人工补充 accepted_names 后，下一次评估才能稳定匹配。

### 9.3 匹配结果

- TP：成功一对一匹配。
- FP：实际有、期望没有，包括重复候选。
- FN：期望有、实际没有。
- ambiguous：疑似匹配但无法唯一确定；歧义组中的每张实际卡计为 FP、每张期望卡计为 FN，并额外记录 ambiguous_count，避免歧义在指标中消失。

## 10. 字段投影与比较

### 10.1 排除字段

不参与卡片内容评分：

~~~text
id
created_at
updated_at
entity_group_id
review_item_id
run_id
~~~

### 10.2 独立评估字段

- evidence_excerpt 和 evidence_excerpts 进入证据指标。
- 首个评测集只把 candidate_action=create_card 的运行视为完整可评估。
- 运行含 update_card、conflict 或 ignore 时只能降级诊断，不生成综合分；不得把补丁直接当完整卡与金标比较。
- 后续若要正式评估 update_card，评测 case 必须冻结当时已有知识快照，应用层先重建“应用补丁后的预期最终卡”再比较。
- candidate_action 本身只有在评测 case 提供已有知识快照和期望动作时才计分。
- schema_validation 作为运行合规指标展示，不代替内容正确性。

### 10.3 精确字段

适合精确比较：

- type。
- status。
- importance。
- source_origin。
- 章节 ID。
- 类型枚举。
- 布尔和数值字段。

知识卡引用 ID 不跨环境直接比较。evaluation_rules 可以提供 reference_identity_map，把金标逻辑 ID 和实际冻结知识快照解析为规范化身份后比较；没有身份映射或已有知识快照时，该引用字段为 N/A，首轮不计入 structured_field_score。

### 10.4 集合字段

aliases 等 Schema 数组字段使用集合 Precision、Recall、F1。空集合与缺失统一为空集合。

### 10.5 语义字段

以下字段不做整段字符串相等，而交给 LLM 裁判：

- summary。
- source_note。
- identity。
- relationship_summary。
- practice_condition。
- exceptions。
- description。
- 其他 evaluation_rules 明确标为 semantic 的字符串字段。

## 11. 确定性指标

所有比例和分数在存储与 API 中统一使用 0 到 1，N/A 使用 null；计数保持整数。API 对非空浮点保留四位小数，前端只负责乘以 100 并格式化为百分比。任何一层都不得混用 0～1 与 0～100。

### 11.1 候选识别

~~~text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 × Precision × Recall / (Precision + Recall)
~~~

边界：

- 实际和期望都为空：该类型标记 N/A，不进入宏平均。
- 实际为空、期望非空：Precision=0、Recall=0、F1=0。
- 实际非空、期望为空：Precision=0、Recall=N/A、F1=0。
- 总体使用八种类型合并后的 micro 指标。
- 同时展示只统计非 N/A 类型的 macro F1。

### 11.2 结构字段分

~~~text
structured_field_score
= 加权正确字段数 / 加权应评字段数
~~~

字段权重由 evaluation_rules 给出，前端不得自行计算。

没有任何应评精确或集合字段时 structured_field_score=null。

### 11.3 证据指标

- evidence_grounded_precision：实际证据中可以在对应 Markdown 定位的比例。
- expected_evidence_recall：期望证据组中被实际证据覆盖的比例。
- evidence_score：两者的调和平均。

证据覆盖以同章字符区间重叠为准。实际证据不能定位时不得交给 LLM 当作可信来源。

没有匹配卡时 evidence_score=null；存在期望证据但实际没有证据时两个子指标均为 0。

### 11.4 负样本抑制

~~~text
negative_suppression_score
= 未被错误建卡的负样本数 / 负样本总数
~~~

负样本在实际候选中出现时，同时计入 FP。

case 没有负样本时 negative_suppression_score=null。

### 11.5 批量诊断

批量任务额外展示：

- duplicate_candidate_rate。
- merge_miss_count。
- merge_error_count。
- first_seen_chapter_accuracy。
- last_seen_chapter_accuracy。
- source_chapter_coverage。

重复候选已经通过 FP 影响候选 Precision，因此不再重复加入综合分权重。

### 11.6 运行完整度

~~~text
execution_coverage
= 已成功完成的期望章节数 / 期望章节数
~~~

计算规则：

- 单章任务的期望章节数固定为 1；run.status=completed 时成功数为 1，否则为 0，不读取当前恒为 0 的批量计数字段。
- 批量任务按 case.chapter_ids 检查 batch_chapter_progress；status=success 的匹配章节计为成功，不只信任顶层 completed_chapter_count。
- 缺少某个期望章节分支、存在 failed 分支或顶层 failed_chapter_count 大于 0 时，覆盖率不足 1。

它属于评估资格指标，不属于模型内容分。execution_coverage 小于 1 时不生成可比较综合分。

## 12. LLM 裁判设计

### 12.1 裁判边界

LLM 裁判只接收确定性匹配成功的卡片。它负责：

- 判断自由文本是否表达了期望关键事实。
- 判断是否与金标或正文证据矛盾。
- 找出没有来源支持的断言。
- 找出重要事实遗漏。
- 给出结构化、简短、中文理由。

它不负责：

- 决定两张卡是否同一实体。
- 评价文风好坏。
- 猜测正文之外的设定。
- 修改期望卡。
- 决定是否写入 MongoDB。
- 直接计算综合总分。

### 12.2 独立裁判模型

新增配置：

~~~text
EVALUATION_DATASETS_DIR=tests/fixtures/evaluations
EVALUATION_JUDGE_MODEL=
~~~

规则：

- EVALUATION_JUDGE_MODEL 为空但当前默认 LLM 已真实配置时，可以回退到默认模型；若它与生成模型相同，评估记录必须 self_judge=true。
- 裁判专用模型和默认 LLM 都不可用时，方案 B 视为未配置，创建接口返回 503。
- 推荐裁判模型与被评估任务的生成模型不同。
- self_judge 必须比较底层适配器返回的真实 provider 和 model identity，不能只比较 API 请求中的 model_name。
- 知识抽取运行记录的 legacy model_name 字段继续兼容旧 JSON，但新运行只能把它填成实际 model_id；用户请求值如需保留，另存 requested_model_name，不能伪装为已经切换模型。
- 同模型自评仍可生成页面参考分，但 independence_level=same_model，不能作为自动回归门禁。
- independence_level 只允许 different_model、same_provider_family、same_model、unknown。
- 页面不提供一个实际无法生效的模型选择器；只显示后端真实裁判模型。
- 如果未来支持多模型选择，应先扩展模型工厂契约，再开放前端。
- 修改 config.py 和 .env.example 后，必须验证 start.bat。

用户可以显式提交 judge_enabled=false 创建纯确定性评估。此时：

- evaluation_mode=deterministic_only，不检查裁判可用性，也不触发 503。
- judge.model_identity=null、judge.self_judge=null、judge.independence_by_run={}。
- judge_card_total、judge_card_completed 和 judge_batch_count 均为 0。
- semantic_score、semantic_quality_state 和 overall_quality_score 为 null；不能把未执行裁判显示成 0 分或“裁判失败”。
- 仅因为用户关闭裁判不产生 completed_with_warnings；是否带警告仍由诊断任务或其他实际降级决定。
- 页面必须显示“仅确定性评估”，不得把它标成完整方案 B 报告。

生成模型与裁判模型共用规范身份：

~~~json
{
  "provider": "deepseek",
  "model_id": "deepseek-v4-pro",
  "family": "deepseek-v4",
  "endpoint_kind": "openai_compatible",
  "fingerprint": null,
  "known": true,
  "unknown_reason": null
}
~~~

- provider 和 model_id 来自实际创建的底层适配器，不来自前端标签。
- 不保存 API 密钥或带凭据的完整地址。
- 底层无法给出身份时 known=false，并填写中文 unknown_reason。
- AgentRun 保存 generation_model_identity；JudgeCallRecord 保存 judge_model_identity。
- provider 与 model_id 都相同：same_model。
- provider 相同且 family 相同：same_provider_family。
- 两边身份已知且不满足以上条件：different_model。
- 任一身份未知：unknown。
- unknown 与 same_model 一样不能作为自动回归门禁。
- independence_level 按 run_id 逐任务计算并保存；汇总 self_judge 只要任一任务为 same_model 就为 true，unknown 另以身份未知警告呈现，不能被折叠成 false 后当作独立裁判。

模型装配契约固定为：

- 在 application/contracts/llm.py 定义不可变 LLMModelIdentity，并给 LLMContract 增加只读 model_identity 属性。
- LangChainLLMAdapter 构造时必须接收实际 chat_model 与对应身份；它不能从 API 请求中的名称推断身份。
- factory.py 返回包含 chat_model、model_identity 和 configured 的 LLMRuntime；DeepSeek provider 使用传给 ChatOpenAI 的实际 model 参数构造身份。
- create_app 注入测试 chat model 但没有显式身份时使用 known=false、unknown_reason=“注入模型未提供身份”，不得拿 Settings 中的默认模型冒充。
- 裁判工厂使用 EVALUATION_JUDGE_MODEL 覆盖实际 model 参数；配置为空时才复用默认 LLMRuntime。配置了裁判名称但无法真实创建该模型时视为不可用。
- AgentRun 增加 generation_model_identity 和 requested_model_name；旧 JSON 只有 model_name 时，兼容加载器生成 known=false 身份并保留旧值用于展示。

当前知识抽取接口不支持按请求动态切换模型，因此请求行为不再二选一：

- model_name 比较前只去除首尾空白，不做 casefold、别名或模糊匹配。
- model_name 为空时使用应用已装配模型，requested_model_name=null。
- model_name 与已装配 model_identity.model_id 完全相同时允许执行，并原样保存 requested_model_name。
- model_name 与实际 model_id 不同时，在创建 AgentRun 前返回 HTTP 422、错误码 AGENT_MODEL_SELECTION_UNSUPPORTED 和中文消息“当前不支持切换到所选模型，请使用已配置模型”；不得静默忽略请求后继续执行。
- 只有未来模型工厂真正支持按请求创建另一 LLMRuntime 后，才能放开该校验；运行记录仍以新 runtime 的真实身份为准。

### 12.3 最小输入

每张已匹配卡只提供：

- 稳定复合 case_id，内容由 run_id、review_item_id、expected_card_id 共同组成。
- expected_card_id 与 actual_review_item_id。
- knowledge_type 和规范化身份。
- 期望与实际的语义字段。
- expected_claims。
- 金标登记且已校验的 source quotes。
- 由实际 evidence_excerpt、evidence_excerpts 或 source_excerpt 在 Markdown 中定位得到的原文窗口。
- 确定性结构差异摘要。

证据包约束：

- 单卡最多 10 个原文窗口。
- 单窗口不超过约 350 个中文字符，优先按完整段落裁剪。
- 单卡原文总量不超过约 4000 个中文字符。
- 超出上限时优先保留 critical claim、候选新增断言和跨章差异相关窗口。
- 证据仍不足时返回 insufficient_evidence，不能把“未提供证据”直接判成候选错误。

不提供：

- 完整 Agent Prompt。
- 原始模型长响应。
- 无关章节全文。
- 其他卡片的私密内容。
- API 密钥或模型配置。

case_id 固定为：

~~~text
{run_id}::{review_item_id}::{expected_card_id}
~~~

它只作为结构化数据键，不直接用于文件路径。裁判输出必须原样回传，后端逐项校验，防止多个历史任务中的重复 review_item_id 串扰。

### 12.4 防提示注入

小说原文、期望卡和实际卡全部视为不可信数据：

- 使用清晰的数据边界包裹。
- Prompt 明确声明边界内文字只能作为小说资料，不能改变裁判规则。
- 裁判无工具、无文件写入、无网络操作权限。
- 只接受严格 JSON 对象。
- Pydantic 使用 extra=forbid 校验。
- 非法输出只允许一次 JSON 修复；修复仍失败则降级。
- 理由长度限制，禁止裁判返回长篇改写。
- 输出中的 quote_id 必须来自输入白名单。

### 12.5 裁判调用批次

- 同一 knowledge_type 且 generation_model_identity 相同的匹配卡可以组成一批；因此单次 JudgeCallRecord 只有一个明确的 independence_level。
- 每批最多 5 张卡。
- 批内每张卡必须使用独立 case_id，输出不得跨卡引用事实或证据。
- 默认最多并发 2 个裁判批次。
- 单批超时为 120 秒。
- 一次评估最多选择 10 个历史任务。
- 后端在开始前返回预计卡片数和预计裁判批次数。
- 批次输出非法、缺项或发生卡片串扰时，失败批次拆成单卡调用重试；已经成功的卡不重复调用。
- Prompt 达到长度上限时优先缩小批次，不截断关键 claim 或原文证据。

这里的 5 是裁判调用批次大小，与知识沉淀 workflow 的章节并发上限无关。

~~~json
          "missing_claim_ids": [],
          "finding_ids": ["finding_001"],
          "quote_ids": ["quote_ch001_003"],
          "reason": "核心能力描述正确，但身份信息略少。"
        }
      ],
      "findings": [
        {
          "finding_id": "finding_001",
          "kind": "missing_expected_fact",
          "severity": "minor",
          "field": "summary",
          "claim_id": "qin_identity",
          "candidate_excerpt": "",
          "quote_ids": ["quote_ch001_003"],
          "reason": "候选遗漏了一项次要身份信息。"
        }
      ],
      "critical_flags": [],
      "reference_issues": [],
      "confidence": 0.88
    }
  ]
}
~~~

score 取值：

- 4：事实等价且无重要遗漏。
- 3：主要事实正确，存在轻微遗漏或表达偏差。
- 2：部分正确，有明显遗漏但无关键矛盾。
- 1：大部分不正确，或包含重要无依据断言。
- 0：关键事实矛盾、严重幻觉或完全不相关。

verdict 只能为：

~~~text
equivalent
mostly_correct
partial
unsupported
contradictory
not_applicable
~~~

status 只能为：

~~~text
scored
insufficient_evidence
reference_conflict
~~~

Pydantic 使用 status 作为判别字段定义联合类型：

- ScoredJudgeItem：dimensions 必填；field_judgements、findings、critical_flags、reference_issues 为数组；confidence 必填。
- InsufficientEvidenceJudgeItem：dimensions 必须为 null；field_judgements 和 critical_flags 必须为空；missing_quote_ids 与中文 reason 必填；不生成分数。
- ReferenceConflictJudgeItem：dimensions 必须为 null；reference_issues 至少一项；field_judgements 和 critical_flags 必须为空；不扣候选分。

Finding 结构固定为：

~~~text

kind: missing_expected_fact | contradictory_fact | unsupported_fact | out_of_scope_fact | field_semantic_error | weak_evidence | over_merged | incorrectly_split
severity: minor | major | critical
field
claim_id: 可空
candidate_excerpt
quote_ids
reason
~~~

CriticalFlag 结构固定为：

~~~text
code: entity_mismatch | core_fact_contradiction | core_fact_hallucination | future_scope_leakage | unsafe_cross_chapter_merge
field
claim_id: 可空
finding_ids
quote_ids
reason
~~~

ReferenceIssue 结构固定为：

~~~text

~~~

所有 finding_id、issue_id、claim_id 和 quote_id 必须来自本次输入或由后端允许的本次输出命名空间生成；任何未知引用都会使该 item 校验失败。critical 级 Finding 和 CriticalFlag 必须至少引用一个有效 quote_id。

五个通用维度为：

- factual_fidelity：事实忠实度。
- key_fact_coverage：关键事实覆盖度。
- evidence_grounding：证据落地度。
- scope_discipline：范围与确定性纪律，包括后续章节信息污染。
- knowledge_usability：知识卡可用性，不评价文学文风。

批量任务额外使用 aggregation_integrity，判断跨章事实是否正确合并。单章任务必须返回 null，不能用 0 分代替。

LLM 不直接输出百分制单卡分或最终通过结论。应用层根据维度权重计算；field_judgements 只服务差异定位和问题说明。

### 12.7 裁判复核

默认先执行一次裁判。满足任一条件时触发复核：

- confidence 小于 0.75。
- 任一维度或字段 verdict 为 unsupported 或 contradictory。
- 任一维度或字段 score 为 2，处于通过边界。
- 输出缺少输入中的卡片。
- 输出引用不存在的 claim_id 或 quote_id。

复核规则：

- 触发复核后再执行两次独立请求，目标是总计三个有效样本；JSON 修复和传输重试不算独立样本。
- 三个有效样本时，每个维度的最终 score 取三个整数分的中位数，verdict 取至少两票的多数值。
- 三个样本的同一维度最大分差大于 1，或 verdict 没有多数值时，该维度标记 judge_disagreement 并从单卡语义分排除。
- 只有两个有效样本时，仅当 score 完全相同且 verdict 相同时才接受；否则标记 judge_disagreement。
- 只有一个有效样本时，复核未完成，该卡 semantic_status=partial，不生成最终单卡语义分。
- CriticalFlag、reference_conflict 和 critical Finding 至少需要两个有效样本在 code、field、claim_id 上一致才成为正式结论。
- 只出现一次的风险项保留为 advisory finding，不触发硬风险、不扣候选分。
- 普通 Finding 按 kind、field、claim_id 归并；达到多数的 finding 参与最终结论，其余仅进入裁判分歧详情。
- 未触发复核的单次有效裁判可以直接计分，但仍保存 sample_count=1。

### 12.8 裁判失败降级

启动前如果 judge_enabled=true 但裁判模型未配置，API 返回 503 和中文提示，不创建一个伪装成方案 B 的完整评估。只有用户明确改为不启用语义裁判时，才允许创建纯确定性评估。

任务已经启动后，以下情况不使确定性结果丢失：

- 超时。
- 网络错误。
- 非法 JSON。
- 输出条目缺失。
- 裁判分歧无法收敛。

处理结果：

- status=completed_with_warnings。
- semantic_score 为空或只覆盖成功项。
- 保存 judge_coverage。
- 综合分只有在 judge_coverage 达到评测配置阈值时才生成。
- 页面明确显示“语义裁判未完整完成”。

- self_judge。
- independence_level。
- prompt_contract_id。
- prompt_hash。


### 13.2 单卡

~~~text
事实忠实度 35%

证据落地度 20%
范围与确定性纪律 10%
知识卡可用性 10%
~~~

~~~text

证据落地度 15%
范围与确定性纪律 10%
知识卡可用性 10%
跨章节聚合完整性 15%
~~~

~~~text

= 各有效维度的 dimension_score × 对应权重之和
~~~

status=insufficient_evidence、reference_conflict 或 unresolved judge_disagreement 的卡不生成单卡语义分，不能按 0 分处理。

### 13.3 单任务

期望卡 importance 权重：

~~~text
core=4
major=3
normal=2
minor=1
~~~

~~~text
semantic_score
= 各有效单卡语义分 × importance 权重之和
  / 有效单卡 importance 权重之和
~~~

同时保存：

- judge_coverage。
- 各维度宏平均。
- 八种知识类型的语义平均。
- judge_disagreement_count。
- unsupported_claim_count。
- contradiction_count。
- missing_critical_claim_count。
- reference_issue_count。

## 14. 综合参考分

使用稳定配置标识：

~~~text
metric_profile_id = knowledge_extraction_balanced
~~~

默认权重：

~~~text
overall_quality_score
= 0.35 × candidate_f1_micro
 + 0.20 × structured_field_score
 + 0.25 × semantic_score
 + 0.15 × evidence_score
 + 0.05 × negative_suppression_score
~~~

最终质量状态采用短板规则，而不是只看加权平均：

~~~text
final_quality_state
= 运行完整度结论、确定性质量结论、语义裁判结论三者中的最差状态
~~~

因此语义高分不能抵消漏提取，高 F1 也不能抵消关键事实幻觉。综合参考分只用于同一评测口径下的趋势和排序。

质量状态枚举和顺序固定为：

~~~text
high_risk < needs_review < usable < stable
~~~

另有 not_comparable，表示资格不足，不能放入上述质量排序。

确定性质量状态按顺序判定：任一必需指标为 null 时先返回 not_comparable；否则再依次判断 stable、usable、needs_review、high_risk：

- stable：candidate_f1_micro≥0.90、structured_field_score≥0.95、evidence_score≥0.95、negative_suppression_score≥0.90、Schema 合规率=1、ambiguous_count=0。
- usable：candidate_f1_micro≥0.80、structured_field_score≥0.90、evidence_score≥0.90、negative_suppression_score≥0.80、Schema 合规率=1。
- needs_review：candidate_f1_micro≥0.60，且没有确定性硬风险。
- high_risk：低于以上门槛、Schema 合规率不足 1，或存在无法解释的结构冲突。

语义质量状态按以下优先级判定，先命中的规则生效：

1. high_risk：至少两个有效裁判样本确认候选存在 core_fact_contradiction、core_fact_hallucination、future_scope_leakage 或 unsafe_cross_chapter_merge；该硬风险不因平均分缺失而消失。
2. not_comparable：semantic_score、judge_coverage 或必要 critical claim 覆盖任一为空；judge_enabled=false 也直接进入此状态。仅有 advisory 或单次未复核风险不越过本规则。
3. high_risk：semantic_score<0.60。
4. needs_review：存在自评、未知模型独立性、reference_conflict、advisory 风险或 judge_disagreement；这些条件把任何更高分状态封顶为 needs_review。
5. stable：semantic_score≥0.90、judge_coverage=1，且无正式 CriticalFlag。
6. usable：semantic_score≥0.80、judge_coverage≥0.95，且无正式 CriticalFlag。
7. needs_review：semantic_score≥0.60 但未达到 usable。

final_quality_state 计算：

1. 资格条件不满足时为 not_comparable。
2. 确定性或语义子状态为 not_comparable 时，整体为 not_comparable；但已满足两票规则的候选硬风险仍直接为 high_risk。
3. 两个子状态都可比较时，取确定性质量状态和语义质量状态中的较差者。
4. reference_conflict 表示金标与 Markdown 疑似冲突，不扣候选分、不生成该卡语义分；其余覆盖仍满足可比较条件时整体最高为 needs_review，否则为 not_comparable。
5. 只有候选表达与 Markdown 矛盾且经复核确认时，才触发候选高风险。

生成综合分的必要条件：

- 数据集 confirmed 且 checksum 有效。
- execution_coverage=1。
- suggested_card 已成功冻结并通过快照校验。
- 正文哈希一致。
- judge_coverage 不低于 90%。
- 所有包含 critical claim 的匹配卡均完成有效裁判。
- 没有 unresolved judge_disagreement 影响 critical claim。
- 五个加权组成指标均非 null。

任一组成指标为 N/A 或其他条件不满足时 overall_quality_score=null，不重新归一化剩余权重。

参考分级：

- 0.90–1.00：表现稳定，前端显示 90–100。
- 0.80–0.8999：基本可用，前端显示 80–89.99。
- 0.70–0.7999：需要优化，前端显示 70–79.99。
- 0–0.6999：高风险，前端显示 0–69.99。

这些阈值在首轮只用于页面解释。必须使用人工确认的正确卡、轻微遗漏卡、重大遗漏卡、幻觉卡、后续信息污染卡和错误跨章合并卡完成裁判校准后，才能把同一 metric_profile 用作 Prompt 回归或 CI 门禁。

硬风险覆盖分级：

- 任一候选表达与 critical claim 对应正文发生经复核确认的矛盾：最高只能为“高风险”；金标自身与正文冲突则进入 reference_conflict。
- Schema 合规率不足 100%：显示“结构不合规”，即使总分较高也不能标记稳定。
- evidence_grounded_precision 不足 100%：显示“存在无法定位证据”。

前端必须把“综合参考分”中的“参考”二字显示出来，并提供公式说明。

~~~text
│   │   └── {run_id}.json

├── runs/
│   └── {run_id}.json

~~~

- summary.json 只保存列表、进度和聚合所需信息。
- input_snapshot 冻结 manifest、期望卡、评估规则、金标证据、负样本、评分参数、裁判契约、原运行候选和参与评估的 Markdown 正文；_snapshot_manifest.json 登记每个文件的相对路径、字节数、SHA-256 和整体 snapshot_root_hash。
- runs 文件保存任务快照、匹配、差异和任务指标。
- judge_calls 按需读取，不进入默认详情响应。
- 每次进度更新先原子写 judge_calls 和 runs，最后原子替换 summary.json；读取端以 summary.json 的进度为准。
- 中断产生的孤立临时文件可以清理，但不得删除已被 summary.json 引用的审计文件。
- 所有目录由代码按需创建，不使用 .gitkeep。
- 已进入 completed、completed_with_warnings 或 failed 的结果内容不可覆盖；确认和软删除只允许改变 lifecycle。重新评估必须创建新 ID。

所有进入文件路径的 ID 都执行服务端白名单校验：

~~~text

case_id       ^[a-z0-9][a-z0-9_-]{2,63}$
chapter_id    ^chapter-[a-z0-9][a-z0-9_-]{5,127}$
evaluation_id ^knowledge_eval_\d{8}_\d{6}_[a-z0-9]{6}$
run_id        ^extract_run_\d{8}_\d{6}_[a-z0-9]{6}$
call_id       ^judge_call_[a-z0-9]{12}$
calibration_report_id ^judge_calibration_\d{8}_\d{6}_[a-z0-9]{6}$
~~~

- evaluation_id、call_id 和 calibration_report_id 只能由服务端或校准脚本生成；外部传入时仍要重新校验。
- input_snapshot/cases/{case_id}.json 和 input_snapshot/chapters/{chapter_id}.md 写入前必须执行上述校验，并拒绝 Windows 保留设备名、Unicode 规范化后重复和不区分大小写后的文件名冲突。
- 仓库不得把 URL 参数直接拼接为路径；必须先校验 ID，再构造路径，resolve 后确认目标仍位于配置根目录下。
- 数据集相对路径也必须 resolve 后通过根目录包含校验，不能只依赖后缀或字符串前缀。
- 非法 ID 统一返回 EVALUATION_ID_INVALID；不存在的合法 ID 才返回相应 NOT_FOUND。
- 必须测试明文、URL 编码和双重编码的 ../、反斜杠、绝对路径与保留设备名输入。

## 16. 后台任务

LLM 裁判可能需要多次网络调用，因此 POST 不等待完整结果。

返回 HTTP 202 前同步完成：

1. 校验请求、ID、裁判可用性、评测集完整性、任务资格、scope 和正文哈希。
2. 计算 request_fingerprint，并先查询是否已有相同指纹的 pending 或 running 记录；存在时提前返回 409 EVALUATION_ALREADY_RUNNING。
3. 一次性读取评测 manifest、case 输入、metric profile、历史运行、suggested_card 和参与章节 Markdown，并对读取内容再次计算哈希。
4. 在 {evaluation_id}.tmp 目录写入完整 input_snapshot 和 pending / queued summary；此时尚未向调用方暴露 evaluation_id。
5. 重新核对快照根哈希；在仓库原子临界区内再次查询活动指纹，确认无重复后才把临时目录原子重命名为正式 evaluation_id 目录。二次查询发现竞争请求时清理临时目录并返回 409。
6. 注册后台任务；只有快照已持久化且后台任务已成功注册，API 才返回 202。

后台任务只读取 input_snapshot，不再次读取原任务、当前评测集或当前正文：

7. 原子领取 pending 任务，把 status 改为 running、phase=deterministic，完成匹配和确定性指标。
8. 持久化确定性中间结果。
9. phase=judging，按批次调用裁判；每批结束更新 progress 并原子写入。
10. phase=aggregating，计算语义分、综合分和短板结论。
11. phase=finished，设置 completed 或 completed_with_warnings。

任一同步冻结步骤失败时不返回 202，并清理临时目录。正式目录已经重命名但后台注册失败时，也必须在确认任务未被领取后删除这条未对外发布的记录并释放指纹占位；不能向调用方返回一个实际不会执行的 evaluation_id。这样原任务在接口返回后被删除，也不会产生快照竞态。

### 16.1 心跳与进程恢复

- created_at 创建后不变；每次状态、阶段或进度落盘都更新 updated_at。
- 任务从 pending 原子领取为 running 时生成仅供后端使用的 execution_token。领取成功后立即启动独立 asyncio 心跳任务；心跳不得依赖裁判调用、进度回调或主计算协程返回。
- 独立心跳每 15 秒使用“status=running 且 execution_token 仍相同”的 CAS 更新 heartbeat_at；每个裁判批次结束也可额外更新。单批裁判即使等待到 120 秒，心跳仍必须持续。
- 主计算在 finally 中停止并等待心跳任务退出；心跳 CAS 遇到终态或 token 变化时自行退出，不能把终态时间戳覆盖回运行中。
- 可能长时间占用事件循环的 JSON 读写或确定性 CPU 工作必须使用 asyncio.to_thread 或主动让出事件循环，保证独立心跳能够调度。
- pending 的 heartbeat_at 等于创建时间；已返回 202 但 60 秒内仍未被领取的 pending / queued 记录，由看门狗 CAS 转换为 status=failed、phase=finished、error_code=EVALUATION_PROCESS_INTERRUPTED。
- 当前实现是单 FastAPI 进程内后台执行器，不允许多个进程共同领取本地 JSON 任务。服务启动时，遗留的 pending 或 running 记录必然属于已退出进程，立即原子转换为 status=failed、phase=finished、error_code=EVALUATION_PROCESS_INTERRUPTED，lifecycle 保持 draft。
- 运行时看门狗把 heartbeat_at 超过 90 秒未更新的 running 记录按同一规则标记失败；CAS 同时检查旧状态、execution_token 和观察到的 heartbeat_at，避免刚续租或已完成任务被覆盖。
- 页面看到该错误码时显示“评估进程已中断，可基于原快照重试”，不能无限显示“进行中”。
- 若未来切换为多进程或外部队列，必须先引入租约或持久队列；不得沿用上述单进程领取假设。

### 16.2 重试语义

- POST /evaluations/{evaluation_id}/retry 只接受 lifecycle 非 rejected 且 status 为 failed 或 completed_with_warnings 的记录；其他情况返回 409 EVALUATION_INVALID_TRANSITION。
- retry 创建新的 evaluation_id，设置 parent_evaluation_id，不覆盖父记录。
- retry 按字节复制父记录的完整 input_snapshot，并核对 snapshot_root_hash；不得重新读取当前正文、当前评测集、当前 AgentRun 或当前 metric profile。
- retry 只继承输入快照，不复制父记录的 runs 结果或 judge_calls；匹配、指标和裁判调用全部生成新的审计记录。
- 父快照要求启用裁判时，新任务只在能够装配父快照登记的 judge_model_identity 和 prompt_contract_id 时执行；否则返回 503，避免把“同快照重试”悄悄换成另一裁判。
- 用户希望使用当前正文、当前评测集或当前裁判时，必须重新调用普通 POST /evaluations，而不是 retry。
- 同一 parent_evaluation_id 同时最多存在一个 pending 或 running 重试；重复请求返回 409 EVALUATION_ALREADY_RUNNING。
- retry 的 request_fingerprint 由固定字符串 retry、parent_evaluation_id、snapshot_root_hash、裁判身份和 prompt_contract_id 共同计算。

retry 与普通创建共用同一个原子发布函数，顺序固定为：

1. 校验父记录、裁判可用性和活动重试冲突。
2. 生成新 evaluation_id，在 {evaluation_id}.tmp 中逐字节复制父 input_snapshot，创建新的 pending / queued summary，并写入 parent_evaluation_id 和 retry request_fingerprint。
3. 复核每个快照文件和 snapshot_root_hash 与父记录完全一致。
4. 在仓库锁内再次检查同一父记录没有活动重试，再原子重命名发布 pending 目录。
5. 注册后台任务，成功后返回 HTTP 202；响应结构与普通创建相同。

任一步失败都不返回 202：发布前清理临时目录；发布后注册失败则在确认任务未领取后清理未暴露的子记录并释放活动指纹。父记录始终不变。

### 16.3 幂等与并发

普通创建的 request_fingerprint 由 dataset_checksum、排序去重后的 run_ids、judge_enabled、metric_profile_checksum 和实际裁判身份共同计算。相同指纹存在 pending 或 running 记录时拒绝重复创建；终态记录不阻止用户重新评估。指纹只用于并发去重，不作为安全凭证，也不替代快照哈希。

“最终重查活动指纹并发布 pending 目录”必须是 EvaluationResultRepository 的单个原子操作。首轮单进程实现可在仓库级 asyncio.Lock 内重查并发布；冻结失败、竞争失败或注册失败必须清理未暴露目录。若未来支持多进程，必须改为跨进程文件锁或外部队列的唯一键，不能假设进程内锁仍然有效。

### 20.2 快照

- 确认和编辑后确认均不改写 suggested_card。
- 评估只读取 suggested_card，不读取正式知识卡。
- 创建评估后冻结实际候选，后续不再覆盖。
- 删除原运行后评估快照仍可读取。
- 原运行在 202 返回之后立即删除，后台仍只使用已冻结快照完成。
- 202 返回前删除或修改输入会让同步冻结失败，不留下正式评估目录。
- 当前评测集、metric profile 或正文修改、移动、删除后，旧报告仍能从 input_snapshot 完整回放。

- 请求中的模型名称与实际装配模型不一致时返回 422 AGENT_MODEL_SELECTION_UNSUPPORTED，不创建运行、不写入虚假模型身份。

- 任一模型身份未知时 independence_level=unknown，不能进入回归门禁。

### 20.3 匹配

- 同类型同名精确匹配。
- accepted_names 匹配。
- aliases 交叉匹配。
- 不同类型同名不匹配。

### 20.4 指标

- TP、FP、FN 正确。
- 空集合边界正确。
- micro 和 macro 正确。
- exact 字段加权正确。
- 集合 Precision、Recall、F1 正确。

### 20.6 结果仓库与任务

- pending、running、completed、completed_with_warnings、failed 的全部合法状态转换。

- run 子命令始终创建 lifecycle=draft 的报告；达到阈值只设置 passed=true，不自动确认。
- confirm 子命令重新核对报告哈希、模型身份、Prompt 契约和全部阈值，只有 passed=true 才允许把 draft 改为 confirmed；reject 把 draft 或 confirmed 改为 rejected，rejected 不可恢复。

## 22. 完成标准

只有同时满足以下条件，功能才算完成：

- 页面存在“知识沉淀 Agent 效果评估”入口。
- 可选择 confirmed 评测集和多个历史任务。
- 开始前可预检真实裁判身份、逐任务资格、预计卡数和裁判批次数。
- 浏览器不接触任意本地路径。
- 单章与批量任务能自动映射 case。
- 评估创建时会冻结 suggested_card，且作者确认动作不改写原候选。
- 候选 Precision、Recall、F1 可复现。
- 八种类型均有明细。
- 精确字段、集合字段、证据和负样本指标可核对。
- LLM 裁判只评估已匹配自由文本。
- 每个语义结论能追溯到 claim 和 Markdown quote。
- 裁判失败不会丢失确定性结果。
- 自评、裁判覆盖率和裁判分歧在前端可见。
- generation_model_identity、judge_model_identity 和 independence_level 可追溯，未知身份不会伪装成独立裁判。
- 综合参考分公式透明，资格不足时不生成。
- 评估结果冻结实际、期望、评估规则、正文、模型身份和裁判调用，原资料变化后仍可回放。
- 删除原任务后评估记录仍可回放。
- 相同活动请求不能重复创建；进程中断、非法状态转换和严格快照重试都有自动化测试。
- evaluation_id、run_id、call_id 和 dataset_id 的路径穿越测试通过。
- 人工裁判校准集覆盖八种知识类型和六种错误模式，并存在符合第 20.9 节门禁的 confirmed 校准报告。
- rejected 评估不出现在默认列表。
- 无新增 MongoDB 写入。
- 无新增前端第三方依赖。
- 后端测试、前端 lint、前端测试和 build 通过。
- start.bat 在固定端口可以正常启动和验证。

## 23. 后续扩展

以下能力保留扩展入口，但不进入首轮：

- 人工覆核裁判结论并生成新的 confirmed 评测规则。
- 多裁判模型交叉投票。
- token 和费用统计。
- 裁判结果哈希缓存。
- Prompt 或模型趋势曲线。
- CI 回归门禁。
- 为其他 Agent 实现独立 EvaluationStrategy。
- 把评测集制作流程产品化。

扩展时应复用评测集仓库、结果仓库和裁判契约，不把知识沉淀专属字段硬塞进通用任务监控模型。
