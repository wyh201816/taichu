## 2. 当前实现状态

当前代理名称为 `knowledge_extraction`，版本为 `v0.1`，Schema 版本为 `knowledge_fields_v2`，总 Prompt 版本为 `knowledge_extraction_prompt_v2`。

已实现能力：

- 从指定章节读取正文，按章节正文生成一次同步运行。
- 第一版仅处理四类知识：角色、地点、势力、物品。
- 使用三段模型链路：通用提及抽取、角色专家整理、实体专家整理。
- 保存完整运行中间态：节点、模型调用、原始提及、实体聚合、忽略项、候选卡、审核项、指标和错误。
- 作者审核动作已接入：确认新建、确认更新、编辑后确认、废弃候选、删除运行记录。
- 前端工作台已接入运行、候选、详情、指标四个视图，并支持复制或下载完整模型链路 Markdown。
- 持久化采用 JSON 文件：运行记录写入 `project_assets/derived/agent_runs/knowledge_extraction/`。

当前未实现或未完善能力：

- 运行是同步执行，长章节或慢模型会阻塞到请求完成。
- `force` 输入已进入请求和状态，但当前未看到基于内容哈希的重复运行跳过逻辑。
- 角色专家和实体专家按线性顺序调用，未并行。
- 质量闸门依赖规则和名称标记，暂未使用模型做二次判定。
- 冲突检查当前主要检查严格互斥字段，普通字段差异不会形成完整冲突列表。

## 4. 后端运行链路

端到端链路如下：

1. 前端从章节列表选择章节，调用 `POST /api/agent-workbench/knowledge-extraction/runs`。
2. API 调用 `KnowledgeExtractionService.create_run()`。
3. 服务构建 `KnowledgeExtractionDependencies`，注入章节服务、模型、知识仓储和运行记录仓储。
4. `build_knowledge_extraction_graph()` 构建线性 LangGraph。
5. 图从章节读取开始，经过提及抽取、质量闸门、专家整理、校验、冲突检查和已有知识匹配。
6. `WriteIntermediateJsonNode` 把完整 `AgentRun` 写入 JSON。
7. API 返回运行摘要，前端再读取运行详情并展示候选、节点、模型调用和指标。
8. 作者对候选执行确认、编辑确认或废弃时，服务更新知识卡和运行 JSON 中的审核状态。

失败处理方式：

- 每个节点由 `_node()` 包装，自动记录开始时间、结束时间、耗时、输入摘要、输出摘要和错误。
- 前序节点失败后，除 `WriteIntermediateJsonNode` 外后续节点会标记为 skipped。
- 即使模型响应不是合法 JSON，运行也会写出失败中间态，便于回放问题。

## 5. LangGraph 节点清单

| 顺序 | 节点 | 类型 | 主要输入 | 主要功能 | 主要输出 |
|---:|---|---|---|---|---|
| 1 | `LoadChapterNode` | 数据读取节点 | `chapter_id` | 读取章节正文、标题，计算内容哈希和字数 | `chapter_title`、`markdown_text`、`content_hash`、`word_count` |
| 2 | `SegmentChapterNode` | 预处理节点 | 章节正文 | 正文不超过 6000 字时单段处理，超过时按段落切成约 5000 字片段 | `segments` |
| 3 | `GeneralExtractionNode` | 模型节点 | 正文片段 | 调用通用抽取 Prompt，只发现 raw mentions，不生成最终知识卡 | `raw_mentions`、`raw_candidates`、`ignored` |
| 4 | `MentionNormalizeNode` | 规范化节点 | `raw_mentions` | 清洗类型、名称和证据；证据截断到 300 字；无效提及转入忽略项 | 规范化后的 `raw_mentions` |
| 5 | `EntityAggregationNode` | 聚合节点 | 规范化 mention | 按知识类型和规范化名称聚合同一实体 | `entity_groups` |
| 6 | `CandidateQualityGateNode` | 规则闸门节点 | `entity_groups`、已有 active 知识 | 先匹配已有 active 知识，命中则放行；否则按类型规则过滤泛称、普通地点、普通物品等 | 更新质量判定后的 `entity_groups`、初步 `raw_candidates` |
| 7 | `TypeDispatchNode` | 分发节点 | 通过质量闸门的实体组 | 拆分角色组和实体组 | `character_entity_groups`、`entity_entity_groups` |
| 8 | `CharacterExpertNode` | 模型节点 | 角色实体组、角色 schema | 生成角色知识卡草稿或更新建议 | 角色 `typed_candidates` |
| 9 | `EntityExpertNode` | 模型节点 | 地点、势力、物品实体组、已有 active 摘要、实体 schema | 生成地点、势力、物品卡草稿或更新建议 | 实体 `typed_candidates` |
| 10 | `NormalizeAndValidateNode` | 校验节点 | `typed_candidates` | 补默认状态和来源，检查禁用字段、必填字段、类型范围、未知字段和证据长度 | 带 `schema_validation` 的候选 |
| 11 | `RunInternalConflictCheckNode` | 本轮冲突节点 | `typed_candidates` | 检查同一轮内同类型同名重复候选 | `internal_conflicts` |
| 12 | `MatchExistingKnowledgeNode` | 已有知识匹配节点 | 候选、active 知识仓储 | 按名称和别名匹配已有 active 知识卡；命中后设置目标卡和外部冲突 | `target_card_id`、`matched_card_name`、`external_conflicts` |
| 13 | `BuildReviewItemsNode` | 审核项构建节点 | 校验后的候选 | 根据校验、冲突、是否命中已有卡，生成作者可处理的审核项 | `review_items` |

## 6. 候选动作判定

候选进入作者审核前，会统一转换成 `AgentReviewItem`：

- 结构校验失败：`ignore`，建议忽略，不能直接确认入库。
- 存在本轮冲突或已有知识冲突：`conflict`，必须编辑后确认。
- 命中已有 active 知识卡且无冲突：`update_card`，建议补充已有卡。
- 未命中已有 active 知识卡且无冲突：`create_card`，建议创建新卡。

作者动作的写入规则：

- 直接确认新卡会调用 `create_active_card()`。
- 直接确认更新会调用 `apply_author_confirmed_updates()`，默认追加。
- 编辑确认可以选择追加或覆盖，并可显式指定目标知识卡。
- 废弃只改变审核项状态，不删除候选和运行回放数据。

## 7. 模型链路分析

当前模型链路最多三次调用：

| 调用 | 节点 | Prompt 版本 | 输入 | 输出 | 作用 |
|---:|---|---|---|---|---|
| 1 | `GeneralExtractionNode` | `general_extraction_v2` | 章节片段、章节标题、允许类型 | `mentions`、`ignored` | 只负责发现原文中的角色、地点、势力、物品提及，不负责生成知识卡 |
| 2 | `CharacterExpertNode` | `character_expert_v2` | 通过质量闸门的角色实体组、角色字段 schema | `cards` | 把角色实体组整理成结构化角色候选 |
| 3 | `EntityExpertNode` | `entity_expert_v2` | 通过质量闸门的地点、势力、物品实体组、实体 schema、已有 active 摘要 | `locations`、`factions`、`items` | 把非角色实体整理成结构化候选 |

这种设计的优点：

- 通用抽取和卡片整理分离，可以先过滤低价值提及，再让专家 Prompt 处理更少的候选。
- 角色与非角色分开整理，避免一个 Prompt 同时维护所有字段。
- 每次模型调用都完整记录 prompt、raw response、parsed output、耗时和错误，便于复盘。
- 专家节点在没有对应实体组时会跳过，避免无意义模型调用。

这种设计的代价：

- 真实样本中三次调用串行，总耗时约 151 秒，其中模型调用占绝大部分。
- 通用抽取 Prompt 较长，专家 Prompt 还携带 schema 和实体组，输入体积会随候选增长。
- 地点、势力、物品共用一个实体专家 Prompt，单次输出结构更复杂，模型出错时影响三类候选。
- 质量闸门在专家节点前执行，规则误杀会导致后续模型没有机会修正。

## 9. 质量闸门机制

质量闸门的当前优先级：

1. 类型必须属于第一版范围。
2. 名称和证据必须存在。
3. 如果名称或别名命中已有 active 知识卡，则直接接受，作为更新候选。
4. 否则按类型规则判定是否接受。

类型规则概览：

- 角色：拒绝泛称、人群、相对指代；多次出现、明确称号、2 到 5 字稳定专名、原文直接命名可接受。
- 地点：拒绝普通功能空间和泛地点；包含镇、岭、山、门、铺、谷、洞、峰、城、街、院等稳定空间标记且长度足够时接受。
- 势力：拒绝泛称人群；包含教、宗、门、派、族、家、会、盟、国、朝、院等组织标记时接受。
- 物品：拒绝普通消耗品、银两、衣物、器具；包含令、牌、丹、药、剑、符、珠、黄精、法宝等特殊物品标记时接受。

当前问题：

- 规则成本低、可解释，但对世界观中“国家”“考核用具”“规则性物品”的召回不足。
- 如果已有 active 卡已存在，闸门会放行更新；如果尚未存在，首轮抽取更容易被规则误杀。
- 地点和势力在“国家/宗门/政权”类实体上边界不够清晰。

## 10. Schema 与字段边界

第一版明确不让正文沉淀代理维护以下字段或结构：

- `body`、`tags`、`fields`、`confidence`、`source_refs`。
- `relations`、`foreshadow`。
- `personality`、`motivation`、`appearance`。
- `current_goal`、`secret`、`known_secrets`。

候选必须满足：

- 类型属于角色、地点、势力、物品。
- 必须有 `name`、`summary`、`source_note`、`evidence_excerpt`。
- `source_origin` 必须是 `agent_extract`。
- 单条 `evidence_excerpt` 不能超过 300 字。
- 不允许输出未知字段。

这套边界与知识卡字段重构规则一致：正文沉淀只负责生成可审核的结构化事实，不负责维护复杂关系、伏笔、秘密、动机和正文正文体。

## 11. 冲突与匹配分析

已有知识匹配通过 `search_active_identity()` 完成，策略是同类型下名称和别名规范化后精确命中。命中后：

- 设置 `target_card_id`。
- 设置 `matched_card_name`。
- 设置匹配原因。
- 检查外部冲突。

严格冲突字段：

- 角色：`death_chapter_id`。
- 地点：`controlling_faction_id`。
- 物品：`current_holder_id`。
- 势力：当前没有严格冲突字段。

实现风险：

- `_external_conflicts()` 当前在检查严格冲突字段后直接返回，后面的普通字段差异比较逻辑不会执行。因此目前外部冲突实际只覆盖严格字段，不覆盖 summary、identity、leader_id 等更广泛差异。
- 本轮内部冲突只检查同类型同名重复候选，不检查同一实体被拆成不同别名、不同类型或近似名称。
- 匹配是精确规范化匹配，不做模糊匹配，别名缺失时可能把已有实体当成新卡。

## 12. 前端工作台实现状态

工作台页面已经能支持作者完成完整审核链路：

- 运行任务：选择章节，创建新运行，查看历史运行，删除运行记录。
- 待处理候选：按待处理、已确认、已废弃、全部筛选候选。
- 候选详情：展示类型、动作、状态、原文证据、校验错误、目标卡、建议 JSON。
- 作者动作：确认、编辑后确认、废弃。
- 运行详情：展示节点顺序、节点状态、模型调用、Prompt、原始响应、解析结果、原始提及、实体聚合和忽略项。
- 评测指标：展示候选总数、各类型数量、创建/更新/冲突数量、结构校验结果、处理状态、模型调用次数、总耗时、节点耗时。
- 链路导出：可以复制或下载完整 LLM 链路 Markdown。

需要注意：

- 工作台主要是调试和作者审核界面，不是普通读者可见页面。
- 前端候选编辑本质是编辑 JSON 草稿，对作者要求较高；后续可以拆成结构化表单。
- 运行创建是同步请求，长耗时期间前端只能显示运行中状态，体验取决于 HTTP 超时和模型响应速度。

## 13. 后续建议

优先建议：

1. 修复或明确 `_external_conflicts()` 的返回逻辑，决定是否需要恢复普通字段差异冲突检查。
2. 为“国家/政权”和“规则性工具物品”补充第一版策略，至少避免 `翔龙国`、`仙灵花` 这类可复用设定被无声过滤。
3. 将角色专家和实体专家改为可并行执行，降低样本中约 90 秒的串行等待。
4. 为质量闸门增加“低置信但进入审核”的动作，而不是只能 accepted/rejected，避免规则误杀有价值设定。
5. 对 `force` 建立明确语义：同章节同内容是否复用已有运行、是否强制重新生成。

中期建议：

- 为候选编辑提供结构化表单，降低作者直接编辑 JSON 的成本。
- 为实体匹配增加别名推荐或模糊匹配提示，但最终仍由作者确认。
- 将完整 Prompt 和 raw response 的展示做脱敏或折叠策略，避免工作台在长文本下卡顿。
- 补充样本集评估，分别统计角色、地点、势力、物品的召回和误杀。
- 增加“被过滤项复活为候选”的作者入口，方便从 ignored 或 rejected entity group 中补回知识卡。
