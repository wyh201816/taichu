# 通用写作智能体全模型评测与审计重构报告

> 更新时间：2026-07-29

## 一、结论

本轮已用 Pico 的“固定任务合同—隔离执行—硬门禁判定—失败分类—工件冻结—指标聚合—真实模型对照”思路，替换太初原有的通用写作助手效果评测实现。旧接口、旧状态、旧前端入口、旧测试、旧夹具和旧运行结果已退出当前链路；现有任务监控继续负责运行时审计，新评测体系专门回答“太初设计的通用 Agent 能力是否被真实执行并满足合同”。

最终模型目录覆盖为 **10/10**：

- DeepSeek V4 Pro、DeepSeek V4 Flash 完成 23 条完整套件，结果均为 23/23。
- GPT-5.6 Terra、GPT-5.6 Luna 完成 23 条完整套件，结果均为 17/23。
- GPT-5.6 Sol 完成 23 条完整套件，结果为 9/23。
- Claude Opus 4.6、Claude Opus 4.7、Claude Opus 4.8、Claude Sonnet 4.6、Claude Sonnet 5 均完成一条真实接入探针，但请求被提供商端点拒绝，模型调用完成数为 0。因此它们只能标记为“提供商接入阻断”，不能据此判断模型能力合格或不合格，也不能进入能力排名。

前端“通用写作智能体评测”页面现已展示每个模型的：

- 任务通过数、评测范围和资格状态；
- 模型调用完成数、失败数和提供商错误数；
- 平均响应时间、P50、P95、整套墙钟耗时和累计模型响应耗时；
- 输入、缓存输入、输出、推理和总 Token；
- 费用金额、币种、费用是否可计算及不可计费调用数；
- 工具步骤、子智能体步骤、请求等待上限和透明重试次数；
- 六类硬门禁通过数、失败类别、失败案例、运行标识、工件引用和工件哈希。

这份结果是“同一份太初代码、同一套 23 条固定合同、同一夹具、同一评测超时和重试策略”下的一次冻结证据，不是对模型的通用排行榜，也不是对模型长期稳定性的最终结论。

## 二、为什么原结果不能直接宣称“所有模型都通过”

复查开始时，现有比较证据只覆盖了两个完整模型运行和一个单条探针，不能代表前端模型目录中的十个模型都已评测。原页面也没有完整展示 Token、费用、响应时间分位、调用失败和证据范围，容易让“列表中出现了模型”被误解为“模型已经完成能力评测”。

真实运行还暴露出四类必须拆开的状态：

1. 模型完成完整套件并通过全部合同；
2. 模型完成完整套件，但部分任务未通过；
3. 提供商调用成功过，但运行中存在可恢复或不可恢复错误；
4. 请求在提供商端点即被拒绝，根本没有进入模型能力评测。

因此，本轮没有继续使用一个模糊总分，而是分别保存评测范围、资格、通过率、提供商错误、硬门禁、Token、耗时和费用。

### 3.2 每条任务在独立工作区执行

执行器会复制固定夹具到新的评测工作目录，再启动通用 Agent。前一次任务的正文修改、结构修改、知识候选、运行记忆和检查点不会污染下一条任务。

这与 Pico 每次复制 fixture repo 的目标一致：同一任务可重复运行，判定不依赖上一次遗留状态。

### 3.3 合成资格轨道先验证 Harness

合成基线使用固定脚本输出，先验证：

- 任务合同可执行；
- Runtime、工具和子智能体调用链可运行；
- 六类硬门禁判定稳定；
- 工件能够生成、落盘、索引和重新水化；
- 同一代码、套件和夹具身份能够复现。

最终合成基线为：

- 运行标识：`synthetic_baseline_33f1433849e61fdc9c5dffd51ab6d87b`
- 结果：23/23

合成基线只证明评测 Harness 自身闭环，不作为真实模型能力结果。

### 3.4 真实模型轨道不与合成结果混写

真实模型轨道调用太初生产通用 Agent Runtime，但使用独立的评测执行策略：

- 单次请求等待上限：120 秒；
- 提供商透明重试：0 次；
- 禁止模型回退；
- 评测超时、重试策略和环境身份写入工件并参与哈希；
- 成功调用、失败调用、Provider 错误和回退状态分别记录。

生产环境原有的超时和重试配置没有被改变。评测采用更严格且可复现的边界，避免一个失败请求被 600 秒等待和多次透明重试放大为不可控的整套运行。

### 3.5 单条任务采用六类硬门禁

一条任务只有同时满足以下条件才算通过：

1. 预算门禁：模型、工具、子智能体和总动作未超合同预算；
2. 验证器门禁：结果满足任务语义和机制断言；
3. 产物门禁：合同要求的产物真实存在；
4. 停止原因门禁：运行以合同允许的正常原因结束；
5. 授权安全门禁：读写、外部访问和高风险操作遵守权限边界；
6. 证据门禁：轨迹、调用、产物和验证结果能够互相引用并形成闭环。

Agent 自己回复“完成”不等于任务通过。六类条件独立计算，Provider 失败不会再被错误地同时标成预算超限和安全违规。

### 3.6 失败类别独立保存

当前失败类别包括：

- `budget_exceeded`：超出合同预算；
- `verifier_failed`：验证器不通过；
- `missing_artifact`：缺少合同产物；
- `failure_stop_reason`：异常停止。

页面将这些内部枚举转换为中文。失败类别用于解释任务为什么未通过，不替代原始 Provider 错误和案例轨迹。

### 3.7 工件和聚合层

证据链包含：

- 套件工件；
- 单次运行工件；
- 每条案例结果和证据包；
- 首轮真实闭环工件；
- 多模型比较工件；
- 索引与内容哈希。

聚合层只比较身份一致的候选：代码、套件、夹具、预算、请求等待、透明重试、禁止回退策略必须相同。部分通过的完整运行也必须进入比较，避免只留下成功模型造成“幸存者偏差”。

## 七、审查中发现并修复的问题

### 7.1 模型目录覆盖不完整

原比较证据不足以支持“所有模型都测过”。本轮把前端目录中的十个模型作为必须精确覆盖的闭包，比较工件缺少、重复或增加任一模型都会被拒绝。

### 7.2 前端缺少 Token、耗时、费用和失败上下文

原页面容易只看到通过状态。现已把模型调用、响应时间分位、Token 细分、费用口径、失败案例、证据范围和工件身份全部加入模型详情。

### 7.3 Provider 阻断被混入能力结论

新增 `capability_probe` 与 `blocked` 语义。没有成功模型调用的 Provider 拒绝只能证明接入不可用，不能进入能力排名。

### 7.4 评测复用了生产环境的长等待和透明重试

早期真实运行复用了 600 秒等待和两次透明重试，一次失败调用可能占用数分钟，且策略没有参与工件身份。本轮改为评测专用 120 秒、零透明重试，并将策略写入工件和哈希；生产配置保持不变。

### 7.5 六类门禁曾被错误耦合

旧判定会把任意 Runtime 失败同时写成预算失败和安全失败。现已逐条件计算。以 Claude Provider 拒绝为例，预算、安全和证据门禁仍可通过，只有验证器、产物和停止原因门禁失败。

### 7.6 部分通过候选曾被错误排除

冻结器一度把“套件未全部通过”误认为“套件没有执行完成”，这会只留下成功模型，形成幸存者偏差。现以 23 条案例全部进入终态作为完整运行标准，17/23 和 9/23 都会进入比较并明确标记为部分通过。

### 7.7 可恢复 Provider 错误曾导致错误拒绝

完整成功运行中可能保留一次已恢复的 Provider 错误。现要求调用日志与错误引用严格对称，但不再因为存在已恢复错误就否定最终 23/23；错误次数仍在页面和排序依据中保留。

### 7.8 代码身份曾覆盖不足

新增评测代码快照，哈希实际参与评测的 `src/taichu`、依赖锁、套件夹具和运行脚本，也覆盖尚未提交但真实存在的文件。文档和前端展示噪声不再无意义地改变 Runtime 身份。

### 7.9 合成基线曾与代码变更失去绑定

合成运行身份现包含真实代码快照。门禁或执行语义改变后，旧合成结果不会继续被当作当前资格基线。

### 7.10 并行探针曾造成错误超时印象

早期并发探测曾让 Sol 和 Terra 出现超时，串行复核后 Sol 单条探针能够通过。最终证据全部使用受控执行策略，不把资源竞争造成的偶发超时直接解释成模型能力。

## 十一、面试表达口径

太初把通用写作 Agent 的评测拆成合成资格轨道和真实模型轨道。23 条固定任务先定义用户原文、能力调用、预算、期望产物、验证器、授权边界和证据要求；执行器在隔离夹具中运行 Agent，用预算、验证器、产物、停止原因、安全和证据六类硬门禁判定单条任务。每次运行继续冻结代码、套件、夹具、模型、请求策略、Token、耗时、费用、Provider 错误和完整轨迹，再由聚合层生成全模型比较。这样既能证明 Harness 自身稳定，也能说明每个真实模型在相同合同下完成了多少任务、失败在哪里，并且不会把 Provider 接入失败包装成模型能力结论。

## 十二、2026-07-29 统一决策口径

### 12.1 评测服务的决策

这套评测只服务太初研发人员，用于回答三个问题：

1. 通用 Agent 的真实主链路是否在线；
2. 后端 Runtime、能力调用、上下文治理、人工中断、检查点和恢复设计是否合理；
3. 新模型接入后，能否在同一固定基线下查看合同完成情况、接入可用性和必要的资源数据。

直接产出仍是通用 Agent 评测页及其可追溯工件。页面用于研发定位和后续模型接入观察，不是面向作者的模型选购页。

### 12.2 评测不服务的决策

- 不接线上真实流量；
- 不长期追踪模型的动态效果；
- 不用一次冻结运行代表模型的长期稳定性；
- 不形成模型排行榜；
- 不把能力、可用性、成本、时延和 Token 合成为单一总分。

固定流程仍是先用不变的合成基线验证 Harness，再用固定套件运行真实模型。合成基线只证明评测链路完整、稳定和可复现，不证明真实模型能力。

### 12.3 成功标准

成功不是展示“哪些模型赢了”，而是：

- 固定合同能够真实执行并留下完整证据；
- 发现 Agent 架构、Runtime、上下文、网关或 Harness 缺陷时，先修复系统再复验；
- 不为了得到更多“通过”而放宽门禁、改变合同或隐藏 Provider 错误；
- 页面只展示研发判断需要的运行范围、合同完成、接入状态和必要资源数据。

`passed（通过）`只表示该次运行满足固定合同和六类硬门禁；`failed（未通过）`表示真实运行已经发生但合同未闭合；`blocked（接入阻断）`表示请求未成功进入模型推理。三者用于定位链路，不作为模型能力排名。

### 12.4 门禁与权重

- 23 条任务不设置权重。
- 预算、验证器、产物、停止原因、授权安全和证据六类门禁对首轮合同履约已经足够。
- 输出质量、一致性、引用真实性和长周期状态一致性暂不新增为硬门禁，避免把主观判断过早混入确定性合同。
- 页面已取消名次、排序依据和“提前排名”文案；2026-07-28 历史比较工件中的排序字段为不可变历史兼容字段，当前页面不再消费其排名语义。

## 十三、23 条合同的代表性与未覆盖范围

当前 23 条合同不宣称覆盖所有小说写作请求。它们优先验证最容易暴露 Agent 架构错误的能力边界：

- Runtime 能否按请求选择最小充分执行路径；
- Tool 和子 Agent 是否真实调用并遵守契约；
- 动态 DAG、并行、校验、修复和人工中断是否正确收敛；
- 当前请求、工作记忆、来源证据和写入授权是否保持边界；
- 检查点恢复是否避免重跑已成功节点。

当前已经有专项结构测试覆盖：

- 30 轮历史消息和 20 个节点输出下的固定裁剪顺序；
- 工作记忆检索、过期、拒绝、替代和修复投影；
- 历史记忆摘要与省略计数；
- 大节点输出的结构化压缩；
- 压缩器失败后的非空安全摘要；
- 稳定记忆与当前请求不可截断，超预算时明确拒绝；
- 同一快照在身份未变化时复用。

2026-07-29 复验中，相关上下文、记忆投影和评测单元测试共 **171 个通过**。

但固定 23 条真实模型套件尚未覆盖以下端到端问题：

- 长上下文续写的内容质量；
- 长周期记忆一致性；
- 当前请求很长、工作记忆很长、历史记忆很长三种独立压力场景；
- 发生压缩后，真实模型的合同完成能力和事实保持能力是否仍在线；
- 不同上下文预算、截断阈值和压缩阈值对真实模型行为的影响。

这些缺口应作为独立上下文专项评测，不直接扩充首轮六类硬门禁。专项需要分别控制五层输入体量，记录压缩前后任务完成、关键事实保留、错误引用和 Token 变化，再根据证据调整显式预算；不得为了让模型通过而删除关键上下文或放宽合同。

## 十五、可用模型差距与缓存 Token 解释

### 15.1 差距首先来自执行链路，不等于纯模型能力差距

2026-07-28 原始工件中的调用证据如下：

| 模型 | 协议 | 完成/尝试 | 能力步骤 | 输出 Token | Provider 错误 |
| --- | --- | ---: | ---: | ---: | --- |
| DeepSeek V4 Pro | `anthropic_messages` | 56/56 | 48 | 57,441 | 0 |
| DeepSeek V4 Flash | `anthropic_messages` | 58/59 | 56 | 59,672 | 1 次 `LLM_CALL_FAILED` |
| GPT-5.6 Terra | `openai_responses` | 45/51 | 54 | 30,585 | 4 次拒绝、2 次调用失败 |
| GPT-5.6 Luna | `openai_responses` | 47/53 | 71 | 38,913 | 4 次拒绝、2 次调用失败 |
| GPT-5.6 Sol | `openai_responses` | 25/42 | 31 | 26,724 | 12 次上游错误、4 次拒绝、1 次调用失败 |

差距由至少四类因素共同产生：

1. Provider 可用性不同。Sol 的 17 次 Provider 错误使大量任务在完成规划、能力调用或校验前提前停止。
2. 模型生成的计划和修复路径不同。Luna 产生 71 个能力步骤，Sol 只有 31 个；调用深度和是否进入重规划直接影响耗时、Token 和合同闭合。
3. 完成的模型调用数不同。失败较早的运行可能 Token 更少，但这不是更高效，而是链路没有完成。
4. 输出长度不同。DeepSeek 两个型号输出约 5.7 万到 6.0 万 Token，GPT 三个型号约 2.7 万到 3.9 万 Token，反映它们在结构化规划、子 Agent 和校验阶段的响应长度不同。

因此，当前报告只能说明“这次端到端运行为什么不同”，不能把全部差距归因成模型推理能力强弱。

### 15.2 两种协议的缓存字段含义不同

缓存 Token 差距最大的根因是协议口径：

- `anthropic_messages`：`input_tokens` 表示本次新计算的常规输入，`cache_read_input_tokens` 是另列的缓存读取量，两者应相加得到完整提示输入。
- `openai_responses`：`input_tokens` 已包含全部输入，`cached_tokens` 是其中的缓存子集，不能再次加到总输入。

2026-07-28 原始记录中：

| 模型 | 有缓存调用/全部调用 | 原始输入 | 缓存读取 |
| --- | ---: | ---: | ---: |
| DeepSeek V4 Pro | 45/56 | 79,311 | 91,264 |
| DeepSeek V4 Flash | 43/59 | 145,914 | 39,168 |
| GPT-5.6 Terra | 1/51 | 152,263 | 1,792 |
| GPT-5.6 Luna | 2/53 | 177,088 | 4,608 |
| GPT-5.6 Sol | 0/42 | 104,311 | 0 |

DeepSeek Pro 的缓存读取大于常规输入并不矛盾：它表示大量稳定前缀从缓存读取，而本次新增输入较少。GPT 的缓存量很小或为零，只说明该 Provider/协议在这些调用中回报的缓存命中少，不代表模型本身不支持长上下文，也不代表模型能力更差。

同为 `anthropic_messages` 的 Pro 与 Flash 仍有明显差距，是因为两次完整运行的调用路径、提示长度、稳定前缀命中时机和 Provider 缓存行为不同。缓存命中是“协议 + Provider + 请求前缀 + 调用时序”的运行结果，不是独立的模型能力评分。

### 15.3 已修复的归一化错误

原实现把两种协议统一按“缓存是输入子集”处理，造成：

- `anthropic_messages` 的总 Token 没有加缓存读取；
